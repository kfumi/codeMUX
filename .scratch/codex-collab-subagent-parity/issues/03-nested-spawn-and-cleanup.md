# 03 — 孙智能体可见 + 收尾（移除临时埋点、补设计文档）

**What to build:** 当子智能体自己又派了子智能体时，孙智能体同样作为独立轨道出现且内容实时可见（扁平列表，不做缩进，父子关系靠 agent 路径表达）；这条在「声明迟到、先到的通知被缓冲」的路径下也成立。功能验证通过后，移除本轮排查引入的临时诊断埋点（模块与全部调用点），并把「变体 B 的声明源」补进既有子智能体流式设计文档，避免后续维护者重复踩坑。

**Blocked by:** 01 — 子智能体声明收紧：只有派生调用能建轨道；02 — 变体 B 打通：派生即建轨道，父卡片可点进面板

**Status:** ready-for-agent

- [x] 子线程上到达的子智能体活动声明（`subAgentActivity`，`kind=started`）同样建立轨道并登记下一层线程的路由，孙智能体的推理/消息/工具调用可见。
- [x] 嵌套声明在缓冲回放路径下也成立：父层路由登记后回放的缓冲通知里若含声明，能继续建立下一层轨道。
- [x] 孙智能体轨道的标题/副标题同样取 agent 路径；中断与终态映射与直接子智能体一致。
- [x] 同一次嵌套派生重复宣告仍只产生一条轨道；未声明的下一层线程流量保持缓冲而不是丢弃。
- [x] 单测（状态机 seam）覆盖：子路由声明、回放路径中的嵌套声明、孙代理的状态收敛；用例输入取自真实 wire 快照。端到端（假 app-server seam）序列扩展到两层。
- [ ] 手工验收两种变体：以「让 agent 派两个子智能体」的提示各跑一次，确认父卡片、面板内容、状态收敛，且会话里没有伪子智能体条目。
- [x] 本轮排查引入的临时诊断埋点全部移除（独立模块与通知入口/路由判定/事件出口处的调用点），构建与既有测试保持全绿，运行不再产生临时轨迹文件。
- [x] 既有子智能体流式设计文档补一节：`subAgentActivity` 作为声明源的字段语义（`id` = 派生 call id、`agentThreadId` = 子线程、`agentPath` = 显示名来源），并说明两类协作变体并存、不得只按其中一种实现。

**Outcome（2026-09-19）:** 功能与收尾均完成：嵌套声明复用 `observeActivity`（声明永不入 pending 队列，到达即刻生效并回放该线程已有缓冲），孙代理轨道独立且状态自行收敛；`collabTrace.ts` 与 4 处调用点已删除（`npm run build` 与 sidecar 全量用例全绿）；`docs/superpowers/specs/2026-08-28-subagent-streaming-preview-design.md` 增加「变体 B：`subAgentActivity` 作为声明源」小节（含字段语义表与两套变体对照）。

**评审修正:** 评审指出 pending 缓冲按「最旧先丢」裁剪，若把声明也放进去，压力下会把声明本身挤掉、整支内容永久搁置（违反 spec D10）——已改为声明先行处理、永不入队。另据真机轨迹核对：`collabAgentToolCall` 的 spawn **只出现在父线程**（变体 A 的嵌套本就走父路径，已被覆盖），子线程上的 collab item 是它自己的 `wait`/`sendInput` 编排，故不投影；`declared` 声明的副标题合并路径也补了单测。第 6 项（真实会话手工验收两种变体）需要一次带真实 provider 的 Codex 会话，留给用户执行。
