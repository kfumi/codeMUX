# 03 — 尾部挂载窗口（连同导航契约与滚动锚定）

**What to build:**

让长 Session 只把**尾部连续一段**留在渲染树里，从而给内存与每帧成本一个与历史长度无关的上界。被扣掉的历史仍然在数据里——可搜索、可导航、可回退，只是不再占用渲染资源。

这是一张工单而不是三张，因为**隐藏历史行这个动作本身要求导航与滚动锚定同时正确**：单独隐藏行而不改导航，交付的不是半成品，而是一个"点了没反应的死标记"的回归；单独隐藏行而不处理锚定，交付的是一个位置跳变。所以三者是一次交付：

1. **窗口模型**：一个纯函数解析"本帧挂载多少行、上方隐藏多少行、是否被裁剪"。首次提交挂载约 15 行，稳态上限约 60 行，每次触顶增长约 40 行；按 Session 重置，并夹取到实际已加载行数（避免上一会话增长的预算漏进新会话首帧）。首帧门控必须在 render 期派生——由 layout effect 翻转会出现"先挂载全量、再丢弃重建"的三次提交，长会话反而白付一次全量 DOM 的代价。
2. **导航契约**：导航标记的来源改为当前已挂载的消息行。被扣掉的历史**不生成标记**，而是表现为一个明确的「更早历史」延续标记（点它触发窗口增长）。为未挂载的行画标记会产生"点了没反应"的死标记，比缺少标记更糟；因此当存在被隐藏的历史时，即使已挂载部分不足以构成常规标记密度，导航也应保持可见并显示该延续标记。
3. **滚动锚定**：窗口增长会在阅读位置**上方**增加高度，因此与"上方插入历史"共用同一个 pre-paint 锚点（增长前记录滚动高度，在 layout 阶段按高度差修正）。首帧的占位 spacer 只服务"有界后的底部可达"，**不得**按未挂载条数估算——按条数估算的占位与它替代的真实行不匹配，展开时会把可见文本推走，表现为一次页面翻转式跳变。展开窗口后的重新贴底**仅当用户仍处于贴底状态**时执行；用户在有界的那一帧内向上滚动过，必须保留其位置。"待重新贴底"的标记只能从 effect 设置，不得在 render 期写入（并发渲染与双渲染会为一个从未提交的渲染置位，把用户已经翻上去的画面重新拽到底部）。

**不做**（依据是本仓库已有的实测否决与权衡结论，写在这里以免被重新提起）：不做带高度缓存的测量式虚拟化——消息行高度内容依赖且挂载之后仍会变（流式增长、工具组展开折叠、懒渲染），测量式方案需要一整套高度缓存与失效策略，并会与既有的贴底跟随与锚定逻辑互相干扰；不做双向卸载——对话从底部读、在底部流式，卸载视口下方的行只会与贴底跟随打架；不引入任何第三方虚拟化库；不从状态里丢弃历史。本项目的历史整体装载、没有分页，因此同类方案里"先挂载已加载的、再取更旧一页"的两级升级退化为一级，不引入任何新的协议动作。

**Blocked by:** 01（需要它的基准做改动前后对比）、02（窗口会引入被隐藏的历史，必须建立在已经准确且不再每帧读全量布局的导航之上）

**实现要点**（与 spec 的差异均已注明）：绝对事件下标由转换器新增的 `eventIndexOffset` 参数保持（单点推导 `offset + loopIndex`）；窗口预算存 store（`threadWindowSizes`，只影响渲染投影），会话切换由组件卸载清理重置；首帧门控 render 期派生（键缺失 = 首帧）；导航段基准在计数前把窗口扩到全量——「触顶增长」是合法的缓存失效、不计入纯滚动成本，且全量挂载是逐帧成本的最坏情况。

**反向验证**：临时把 `THREAD_WINDOW_EVENT_THRESHOLD` 调成不存在 → 窗口测试 2 条变红（短会话那条本该过）、恢复后 3/3 绿。

**未覆盖**：探针的全量四组（只跑权威 offscreen 组）；真实引擎下滚动期高亮与视口一致（与工单 02 同源，jsdom 证据 + 探针落点间接覆盖）；`revealThreadWindowForEvent` 已接入 store 但当前无生产调用方（会话级搜索不按 msg-N 跳转，留给未来深链）。
