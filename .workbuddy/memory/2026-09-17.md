## 用户回报空闲态读数 —— 根因确定并已修复

**用户空闲态读数**：`{ ow: 1069, cw: 1059, gutter: "stable", oy: "scroll" }`

### 又排除一条：不是"新挂载元素没有占位"

最小复现（同步插入一个全新滚动容器：`overflow-x:hidden` + `overflow-y:scroll` +
`scrollbar-gutter:stable` + 全局 10px 自定义滚动条）：
`sync-right-after-insert` **就已经是占位 10**，rAF-1 / t+100ms / t+500ms / t+1500ms 全部 10。
⇒ 新挂载不产生 0 占位。

### 根因：Chromium 的滚动条在「经典式（占位）」与「叠加式（占位 0）」之间切换

Chromium 源码 `ui/native_theme/native_theme_features.cc` 里有两个特性：
`FluentScrollbar`（Fluent 观感，占位）与 **`FluentOverlayScrollbar`（强制叠加式，不占布局）**。
再叠加 Windows 11 默认开启的「自动隐藏滚动条」，同一个 scroller 会在两种实现间切换。

**关键**：`scrollbar-gutter: stable` 对**叠加式**滚动条预留的就是 **0** ——
**所以它保护不了这种模式切换**，这解释了为什么 CSS 声明看着完全正确、宽度却仍在变。
四次最小复现（`overflow-x` 取 `hidden`/`clip`/缺省，以及不写 `scrollbar-gutter`）的占位
**恒等于滚动条宽度**，反证了"应用里那次 0 占位来自模式切换，而非 CSS 写错"。

### 修复

`desktop-electron/src/main.ts`（该文件内原本没有任何 commandLine 开关，已 grep 确认）：

```ts
app.commandLine.appendSwitch('disable-features', 'FluentScrollbar,FluentOverlayScrollbar');
```

关掉后滚动条统一走 `::-webkit-scrollbar` 自定义那一套，占位恒定，内容宽度不再随
滚动条出现/消失而变。**一行、可逆**（无其它代码依赖它）。

外壳类型检查 `tsc -p tsconfig.json --noEmit` **exit 0**。

## ✅ 最终确认：根因是「减少动效」状态下折叠内容的高度动画退化

**用户实测：把 Windows「动画效果」重新打开后，闪动几乎消失。** ⇒ 根因就是
`prefers-reduced-motion: reduce` 状态本身，与 JS 代码无关。

（顺带说明：`FluentOverlayScrollbar` 那个开关虽然已生效却没治住闪动，是无效假设，已撤回。）

### 机制（本轮补全）

`collapsible-down/up` 是全应用**唯一会改变布局**的动画（它动的是 `height`；其余动效
都只动 opacity / transform / filter）。而 Radix 的 `CollapsibleContent` 由 `Presence`
包裹，`Presence` 按计算后的 `animation-name` 决定"是否等动画结束再挂载/卸载内容"。

reduce 状态下，产物源序让**关闭态**仍带 `animation-name: collapsible-up`，
却把时长压成 **0.01ms** —— 一个退化状态：Radix 在等一个实际上已经结束的动画，
期间折叠内容停留在「height:0、内容被裁切」的中间态，随后才卸载。**布局高度在这个
窗口里来回变 ⇒ 滚动条占位随之变 ⇒ 内容重排 ⇒ 用户看到"变宽变窄 + 滚动条闪动"。**

### 我上一轮的修正方向错了（已改正）

上一轮把它改成 `animation-name: none` —— **等于抽掉了"把高度收到 0"的那一步**，
Radix 卸载前内容反而停在自然高度，布局先涨后缩，**没有治好闪动**。

### 正确修法（已实施）

`globals.css` 的 reduce-motion 块里，对三类折叠内容**保留动画、只恢复真实时长**：

```css
html [data-slot='tool-group-content'],
html [data-slot='tool-fallback-content'],
html [data-slot='reasoning-content'] {
  animation-duration: var(--animation-duration, 200ms) !important;
  animation-iteration-count: 1 !important;
}
```

200ms 的纯高度收合不属于会引起前庭不适的位移类动画，既让 Radix 的握手回到正常
路径，也让 reduce 下的观感与「动画效果打开」一致。

### 验证（headless，真实 reduce 状态 + 真实源序非对称）

把变体类按产物偏移摆出真实非对称（`collapsible-down` 在 motion-reduce 块**前**、
`collapsible-up` 在**后**），同一页里对照"受新规则覆盖"与"不受覆盖"两种情况：

| 状态 | animation-name | duration | 结论 |
|---|---|---|---|
| 关闭态，**有** data-slot（受修正覆盖） | `collapsible-up` | **0.2s** | ✅ 握手正常 |
| 关闭态，**无** data-slot（= 上一版行为） | `collapsible-up` | **0.01ms** | ❌ 退化 |
| 展开态 | `none`（源序使然，符合意图） | — | ✅ 立即挂载 |

## ✅ 新根因：`useScrollLock` 的"隐藏滚动条 + padding 补偿"（解释信号 B + 渐进变窄）

用户反馈：反复快速展开/收起思考时，内容区**越来越窄**、离右边越来越远 —— 渐进累积，
与此前已修的 Radix Presence 闪动（信号 A）是两回事。

### 机制

`@assistant-ui/react` 的 `useScrollLock`（`src/primitives/reasoning/useScrollLock.ts`）被
`reasoning.tsx` / `tool-group.tsx` / `tool-fallback.tsx` 各自实例化，`findScrollableAncestor`
都命中**同一个线程视口**（`CodeMuxThread.tsx:498`，`overflow-y-scroll scrollbar-gutter-stable`，
自定义滚动条 10px）。每次上锁：

1. 写内联 `scrollbar-width: none` —— Chromium 连 `scrollbar-gutter: stable` 的预留**一起塌陷**
   （占位 10→0），同时 `padding-right += 10` 补偿；
2. 200ms 后恢复为**各自捕获的** `previousPadding`。

**渐进泄漏**：同一容器上两个锁的 200ms 窗口重叠时（不同折叠组件、或快速连续操作），
后锁捕获的 `previousPadding` 是前锁写入的 "10px"；前锁先到期恢复为空、后锁后到期把
"10px" 写回 ⇒ **padding-right 永久残留，每重叠一轮 +10px** ⇒ 内容区越来越窄。

**每次点击的 -10px 闪动**：这正是前几轮探针"信号 B"（`ow` 恒 1069，点击瞬间 `cw`=1069
占位 0，+191ms 恢复 1059）的真正来源 —— 当时归因为 Fluent 叠加滚动条模式切换，**错误**
（Fluent 开关实验也确实证伪了）。真相是 lock 窗口内 `scrollbar-width:none` 让占位塌陷为 0，
恢复时回到 10。此前 MEMORY.md 里"`cw` 变 10px 就是滚动条模式在切"的结论一并修正。

### 修复

新增 `src/hooks/useCollapsibleScrollLock.ts`（只保留钉 scrollTop 的有效部分，**完全不
碰滚动条与 padding**——视口滚动条本就常驻，无需隐藏），三个组件的 import 全部换掉。
