## 第二轮（用户反馈"仍掉帧 + 计时器卡住"后）

**关键读法**：用户截图给出 `AgentThread 846 次 commit / 累计 7326ms`，会话约 106s → **React commit 只占挂钟时间约 7%**。这个比例本身就是结论：**瓶颈在 React 之外**，继续优化渲染是错方向。

### 新增修复 ①：客户端事件管线 5 次 JSON → 1 次

**根因**：单个事件在主线程被完整 JSON 处理 **5 次**——
`client.ts:341` 解析 WS 帧 → `daemon-session-bridge.ts:78` stringify 回去 → `subagentStore.ts:233` 解析（仅判断类型守卫）→ `agentStore.ts:1728` 解析（仅判断 `steer_result`）→ `agentStore.ts:1077` 真正解析。

**为何第一轮低估**：按"每事件数十微秒"估算，只看到小 delta；实际由**大 payload × 5** 主导（Read 返回整文件内容、`file_snapshot` 原文件），且**全在 React commit 之外**，Profiler 看不到。

**改法**：`SessionEventHandler` 入参放宽为 `string | Record<string, unknown>`，bridge 直接下传已解析对象；三个消费者仅在入参为字符串时才 `JSON.parse`。**向后兼容**——直连 sidecar 旧路径与全部测试桩仍传字符串。

### 新增修复 ②：`backgroundThrottling: false`（最可能的"计时器卡住"元凶）

`desktop-electron/src/main.ts` 的 `webPreferences` **未设置该字段 → Electron 默认 `true`**。被遮挡/失焦窗口会被 Chromium 当后台页面：rAF 大幅节流（→ FPS 塌到个位数）、`setInterval` 被节流（→ "正在执行 · 12s" 冻结）。

**判据**：单纯 CPU 忙碌只会让 1 秒定时器延迟几十~几百毫秒，**不会冻结数秒**；能让它长时间不动的只有**定时器节流**。

**产品层面为何致命**：CodeMUX 的核心场景就是"agent 跑几分钟，用户切去编辑器"。默认节流正好打在这上面。**副作用**：窗口被遮挡时仍持续合成，后台 CPU 略升，已接受。

**推论**：此前所有在窗口非前台状态下测得的 FPS 读数都可能被节流污染，不可直接当渲染性能结论。

### 新增诊断能力（停止盲猜）

- `PerfOverlay` 加"长任务/秒"（`PerformanceObserver(['longtask'])`）：**区分"真 CPU 阻塞"与"节流"的决定性判据**——FPS 低且长任务 0 = 节流；有长任务 = 真阻塞。
- 接通原先**无人调用**的 `recordIpc`（在 WS `onmessage` 上）：此后"IPC/秒"即**真实入站 WS 帧速率**。

### 验证

前端与 Electron 外壳类型检查通过（外壳 exit 0）；受影响测试 8 文件/142 用例全绿；完整套件仍为**同一对已知抖动用例**（`CodeMuxAssistantRuntime.test.tsx:1701`/`:2049`）超时，属既有负载抖动。

### 仍未修复（按新证据重排）

1. **根因 2 剩余一半**：daemon 逐事件广播、不做帧合并（协议层改动，收益 N 倍，需保留兼容分支）
2. 根因 8：scheduled 会话每秒全量重拉 timeline（**已确认仅影响 `origin === 'scheduled'`**）
3. 根因 9/4/12：属 React commit 内开销，因只占 7% 而**优先级下调**

现场特征：**"读取 6 次文件"**、普通会话（非 scheduled）。

### 两个关键读数结论

1. **长任务非 0 且累计 3543ms ⇒ 主线程真被阻塞**，不是节流。故第八节的 `backgroundThrottling` 修复正确但**不是主因**。
2. **`IPC/秒` 仅 4–12 ⇒ 我此前"每事件一帧、每秒数百帧"的假设是错的**，**daemon 帧合并不值得做**（已从最高优先级改为否决）。

### 真正元凶（根因 18）：逐事件深拷贝整份历史

`convertAgentEvents.ts:903-912` 的 `createEventPart` → `cloneJsonValue` → **`structuredClone(整个事件)`**，被 `:319` 主循环**逐事件**调用；而 `CodeMuxAssistantRuntime.tsx:79` 是 `useMemo([events, ...])`，**每来一个事件就重算并遍历全部历史**。

⇒ 单次转换 O(整份历史负载)；`tool_result` 含 Read 读回的整文件内容时单次要克隆**数 MB**，耗时正好 **~100ms** —— 与四张截图"最长"稳定在 94/102/105/105ms 完全吻合。

**修复**：`WeakMap<AgentMessage, AgentMessage>` 按事件对象身份缓存克隆，每个事件只克隆一次。前提是 store 事件引用稳定（store 只 append/filter，不重建元素）——已核验。

### 方法论教训（已写入 MEMORY.md）

**Profiler 的子树边界必须显式确认。** `<Profiler id="AgentThread">` 在 `AgentPanel.tsx:511`，而 `convertAgentEventsToAssistantMessages` 在其**上层 provider** 里 —— 转换完全不在测量范围内。所以我此前"React 只占 7% ⇒ 瓶颈在 React 之外"方向对，但**把大头错归到了事件管线的 JSON 往返**，真实大头是这个越界的全量深拷贝。

### 顺带修复

另消除 4 处 `JSON.stringify` → `parseAgentEvent` 往返（`agentStore.ts:3357` scheduled 全量加载、`SubagentPreviewPanel.tsx:64`、`ChatSearchDialog.tsx:225`、`sessionTitle.ts:44`）。

### 验证

前端类型检查改动文件零错误；相关模块测试 **7 文件 / 201 用例全绿**。

### 关于"卡 UI 尺寸调整"

非独立问题：resize 触发全 DOM 重排，而主线程已被 ~100ms 深拷贝块打满，重排只能排队。主线程占用下降后应缓解；若仍明显，再查大 DOM（根因 12 无虚拟化）的 resize 布局成本。

## 第四轮：对照 Paseo 项目（`D:\project\my-project\paseo`）

**产出报告**：`docs/research/2026-09-16-paseo-stream-smoothness-analysis.md`（新建）

用户指出 Paseo 架构相似但对话很少严重掉帧。逐行读其源码后，结论是：**它在五个层级各设了边界，CodeMUX 缺四个。**

### 最重要的三条对照（都已在 CodeMUX 侧核验）

1. **体积无界（单项收益最大，且与第三轮元凶同源）**
   - Paseo：`agent-timeline-content.ts:4` `TOOL_CALL_CONTENT_MAX_LENGTH = 64 * 1024`，在**进入管线前**截断 shell output / plain_text / failed error，且**录制与广播共用同一个已截断对象**（`docs/timeline-sync.md:17-20` 明确列为不变量）。
   - CodeMUX：**全 `src-tauri/` 无任何工具输出体积上限**（已检索 `MAX_*_BYTES/CHARS/LEN/SIZE`、`64*1024`、`65536` 等，命中项全部无关）。唯一相关上限是 HTTP body 64MB。
   - ⇒ 第三轮那个「~100ms 深拷贝」的直接来源就是**数 MB 的 `tool_result`**。WeakMap 让"每个事件只克隆一次"，但**单次克隆的成本仍由这个体积决定**。Paseo 是不让这个体积存在。

2. **合并点在"落库+广播"上游**
   - Paseo：`agent-stream-coalescer.ts:3` 60ms 窗口 + `collapseEntries` 把文本增量**语义拼接成一条**；`onFlush → recordAndDispatchTimelineItem`（`agent-manager.ts:752-759`），所以落库/广播/渲染看到的都是合并后的一条。
   - CodeMUX：sidecar 50ms 批处理内是**逐条 `text_delta`**（未拼接），daemon 收到后**把批次摊平回逐条**（`timeline_persist.rs:88-100`，函数文档原话 "batch messages are flattened"），广播**每事件一帧**（`companion/server.rs:1215-1221`）。等于白批一层。

3. **分帧绘制（CodeMUX 完全缺失，是"手感"的直接来源）**
   - Paseo：`agent-stream/text-reveal.ts`。store 存全文，**只有渲染切片被节流**；`computeRevealStep` 每帧释放 `ceil(backlog × elapsed / 150ms)`，下限 1 字符。突发会"追赶"而非"跳跃"。
   - 五条不变量：首次见到整段渲染 / 离开 streaming 立即补全 / 60Hz 对齐 / 剪裁对齐字素簇 / store 存全文。
   - 官方实测（非 CodeMUX 数据）：可见更新间隔 p50 317ms → **17ms**，p95 383ms → **17ms**；CV 4.11 → 1.86；推进文字的帧占比 6% → 87%。
   - **重要认知修正**：前几轮我把非 Claude 的 leading-edge 双触发当成"频率是设计值 2 倍"的问题。**按 Paseo 的框架，那是"批次不均匀"的问题**——减少批次数不会改善观感反而加重不均匀；正确方向是**保持速率、让其均匀落地**。

### 另外两项对照

- **帧边界提交**：Paseo 事件入队 + rAF 提交 + 48ms 定时器兜底（`session-stream-reducers.ts:1877-1895`）。注释明确「rAF 在隐藏标签页不触发，所以要有定时器兜底」—— 这正是第二轮"计时器冻结"的**正确应对方式**（不是把 rAF 当唯一时钟）。CodeMUX 是事件到达即写 store。
- **历史身份稳定**：Paseo store 分 `tail`（历史）/`head`（实时）两个身份域，流式期间 `changedTail === false` 即不 patch `tail`；配合 `areLayoutItemsEquivalent`（`layout.ts:252`）+ `useRevisedHistoryRows`（`history-row-revision.ts:28`）+ `HistoryStreamRow` memo（`view.tsx:229`）。其文档量化：**没有这个 memo 边界时，每次合并 tick 重渲染每个已挂载行，手机上约 50 行 / 每 tick 100–250ms JS**。
- Paseo **没有数据库**：timeline 是内存数组 `{epoch, rows, nextSeq}`，`cloneRow` 是浅拷贝 `{...row}`；持久化交给 provider 自己的 JSONL。另有：事件序列化一次多订阅者复用、selective delivery（只发正在查看的 agent）。

### 建议（报告已按投入产出比分梯队）

第一梯队（小改动、收益大）：① daemon 侧加工具输出体积上限（对齐 64KiB）；② 客户端帧边界提交；③ daemon 不要摊平 sidecar 批次。
第二梯队：④ 新增分帧绘制（纯函数 + 薄 hook）；⑤ 引入"历史身份稳定"不变量（不照搬双数组）。
第三梯队：⑥ 补"平滑度"指标（p95 可见更新间隔 + chars-per-frame CV）+ 种子化 bursty mock。

### 未验证 / 待确认（重要，勿当结论用）

- **没有运行 Paseo、没有测它的 FPS**。"Paseo 很少卡"来自用户观察 + 其自建 e2e 门禁的存在，属推断。
- 报告里的 317ms→17ms 等数字是 **Paseo 团队在 Expo web 上测的**，不是 CodeMUX 实测，只能当量级参考。
- "体积无界是第一瓶颈"是**推断**（基于第三轮 ~100ms 长任务签名与多兆字节克隆量级吻合），非直接测量。建议对照实验：临时把 `tool_result` 截到 64KiB，看"长任务累计"是否显著下降。
- **一处数据矛盾未解决**：`IPC/秒` 实测 4–12，与"每事件一帧、按 token 速率应有数十帧/秒"在数量级上不符。可能该读数取自"读取文件"阶段而非文本流式阶段。**建议在纯文本流式期间重测**，再决定 ③ 的优先级。

- **`file_snapshot.original_content` 不能截断**：初判认为它"只是展示数据"。探查后确认 **daemon 侧 `turn_artifact_summary.rs:96` 用它算增删行统计**，截断会让统计失真。同时确认**回滚不读它**（工作区还原走 `git restore`，对话回退走 Claude CLI checkpoint）。结论：保留原样，不加上限。
- **`persist_and_stamp` 本来就是整批一次取锁、一次 `append_timeline_events`**，并非逐条取锁。所以"daemon 摊平批次"影响的**只是广播帧数**，不影响落库事务次数 —— 这削弱了 ③ 的收益论证。
- **协议里没有 `tool_result` 事件**：Anthropic 的 `tool_result` block 在 `claudeToolEvents.ts:70` 被投影为 **`tool_finished.content`**。热体积在 `tool_finished.content`（Read/Bash 输出）与 `tool_started.input`（Write 的整份文件）。

### 明确否决（不是遗漏）

- **daemon 帧合并（对照文档 ③）**：其收益前置假设（每秒数百帧）已被第三轮实测（`IPC/秒` 4–12）否定。协议层改动风险不低，在假设未重测前不动。**若纯文本流式期间重测得到数百量级，应重新评估。**
- **帧边界提交（对照文档 ②）**：同理，可合并量很小；且分帧绘制已承担"让文字均匀落地"的职责。**分帧绘制的提交成本是真实未知数**（commit 从 20–40/秒升到最多 60/秒），已留 `localStorage['codemux:textRevealHorizonMs']` 作为调节与 A/B 开关。

## 第六轮：分帧绘制导致全应用 loading 动效冻结（用户反馈的回归）

**报告**：`docs/research/2026-09-16-streaming-animation-freeze-fix.md`（新建）

### 现象与根因

用户反馈：改了之后**所有 loading 动效一起失效** —— `DotMatrix` 点阵闪烁、
`.shimmer` 流光、"正在执行 · 46s"、"运行中 · 29s"、左侧面板状态，全部静止。

**根因**：上一轮新增的分帧绘制按 rAF **每帧提交**，每次提交都让 `Streamdown` 对
累积正文重新分块 + 对尾部代码块重跑 Shiki 分词。提交频率由改动前 50ms 窗口驱动的
**20–40 次/秒**升到 **60 次/秒**（最多 3 倍），主线程被吃满。

**为什么是"全应用"一起冻住**：`DotMatrix` 的 SVG `circle` `opacity` 与 `.shimmer`
的 `background-clip: text` 都是**绘制类**动画，**无法卸载到合成线程** —— 合成动画
在主线程忙时仍能播放，绘制动画不能。所以主线程饱和 = 这类动效全停。

**关键前提差异**：Paseo 能在 60Hz 做分帧绘制，是因为它每帧只渲染一个纯文本
`<Text>`，**没有解析成本**。这个前提在 CodeMUX 不成立。

### 修复

| 修复 | 要点 |
|---|---|
| **提交节流** | `useStreamingTextReveal` 只对**提交**（`forceRender`）节流，默认 **40ms ≈ 25Hz**（低于基线 20–40/s ⇒ 净减少）。释放量仍每帧算（纯算术） |
| **跨实例共享闸门** | 模块级 `lastCommitAtGlobal`。`StreamingContent` 跑两个绘制实例（正文+思考），各自计时会错开提交、把频率翻倍 |
| 闸门只延迟不丢弃 | 常驻帧循环下次开闸补上；停止流式时 effect 补全分支兜底。已有测试覆盖 |
| **加载指示器移出热路径** | 流式页脚抽成 `memo` 组件 `StreamingStatusFooter`（props 仅 `startTime`） |
| **度量口径修正** | 只统计**可见更新**（被节流的帧不算停帧，否则 CV 被系统性夸大）；`visibleUpdates`/`updatesPerSecond`/`charsPerUpdateCv`/`updateIntervalP50/P95` |
| 哨兵值 bug | `windowStartedAt` 原用 `0` 表示"未开始"，与合法时间戳 0 冲突 → 改用 `null`（曾使 `updatesPerSecond` 偏大约 4%） |
| 样本缓冲上限 | 2048。浮层只在 DEV 挂载，缺上限时数组以最多 60 条/秒无限增长 |
| 新增 `系统动效` 读数 | `motion-reduce` 命中时显示。`DotMatrix` 与 `.shimmer` 都有 `motion-reduce` 显式禁用 —— 系统级"减少动效"会产生**一模一样**的症状 |

### 新增开关

- `localStorage['codemux:textRevealHorizonMs']='0'` → 关闭分帧绘制（到达即绘制，A/B 基线）
- `localStorage['codemux:textRevealMinFrameMs']='80'` → 进一步降低提交频率

### 验证

新增 5 项提交节流测试（模拟 1 秒流式：**节流下提交 <35 次、关闭节流后 >40 次**，
直接证明闸门生效）+ 平滑度 12 项。`assistant-ui/` + `dev/` 257 项全通过，且**目录
耗时从 89.0s 降到 51.7s**（渲染次数下降的旁证）。

### 教训（已写入 MEMORY.md）

上一轮我在报告里自己写了「分帧绘制的提交成本是一个真实的未知数……值得实测」，
**却仍然带着这个未知数发车**，用户直接撞上全应用动效冻结。**凡是会改变渲染频率的
改动，应先默认关闭或压到保守值，确认无副作用后再提高。**

## 第七轮：动效失效的**真实**根因（推翻了上一轮的结论）

用户反馈"动画效果还是没有恢复"。**取证后确认第六轮的根因判断是错的。**

### 真实根因：系统 `prefers-reduced-motion` + 仓库里的通配 `!important` 规则

**证据一**：用本机 Chrome headless 探测（`--headless=new --dump-dom` 加载一个把
`matchMedia` 写进 DOM 的探针页）：

```
PROBE_RESULT={"reduce":true,"noPreference":false,...}
```

**这台机器的 `prefers-reduced-motion` 就是 `reduce`。**

**证据二**：`src/styles/globals.css:547` 的通配规则经构建后原样进入产物
（`desktop-electron/renderer-dist/assets/index-DLqJS0sO.css` 偏移 262125）：

```css
@media(prefers-reduced-motion:reduce){* ,:before,:after{
  animation-duration:.01ms!important; animation-iteration-count:1!important}}
```

`*` + `!important` ⇒ **每一个元素的每一个动画**都被压成 0.01ms 且只播一次。

两步叠加 = "全应用动效一起失效"，**包括与渲染路径完全无关的左侧面板**。
而这些动效的代码路径（`dot-matrix.tsx`、`RunningElapsed.tsx`、`ProjectExplorer`、
`SidePanel`）前几轮**一处都没动过**。

### 修复（`globals.css`）

装饰/入场/骨架动画照旧停掉；**负载类动画（转圈、点阵、流光、运行中脉冲）保留但降速
到 2.4s 的呼吸级** —— 因为在本应用的核心场景里它们承载"还在运行"这一**信息**，完全
静止等于信息丢失。

两个必须记住的点：

1. **特异性**：状态规则加 `html` 前缀（0,1,1）即可稳定压过通配规则（0,0,0），
   **不必**把通配规则改写成 `:not()` 列表（那要把名单重复三遍，易错难审）。
2. **光恢复 `animation-duration` 不够**：`DotMatrix` 圆点带
   `motion-reduce:[animation-name:none]`、`.shimmer` 带 `motion-reduce:animate-none`
   （即 `animation: none`）—— 这两处**把动画名也清掉了**，必须把 `animation-name`
   一并写回。**这一点是第一版探针跑出来才发现的**（当时读数 `name=none`）。

### 验证（在本机真实降级路径下，非模拟）

| 元素 | name | duration | 次数 |
|---|---|---|---|
| DotMatrix 圆点 | `aui-dot-matrix-blink` | 2.4s | infinite ✅ |
| `.shimmer` | `shimmer` | 2.4s | infinite ✅ |
| `.animate-spin` | `spin` | 2.4s | infinite ✅ |
| `.animate-pulse` | `pulse` | 2.4s | infinite ✅ |
| 装饰性 `.animate-in` | `fade-in` | **0.01ms** | **1** ✅ 仍停用 |

回归抽查 `assistant-ui/` + `dev/` **262 项全通过**。

### 两条可复用教训（已写入 MEMORY.md / 技能）

1. **先问"环境是否已经禁用了动画"，再谈渲染成本。** 我把"绘制类动画在主线程饱和时会
   冻住"这个**正确的一般事实**直接套到本次故障上，没有先测环境 —— 而一条
   `*, * { animation: none !important }` 就在仓库里躺着，我读了 `globals.css` 的其它
   部分却跳过了它。
2. **headless 探针法是排查环境类症状的利器**：本机 Chrome
   `--headless=new --dump-dom` 加载一个把 `matchMedia` 结果写进 DOM 的探针页，
   可确定性读回 `prefers-reduced-motion` / `prefers-color-scheme`，与 Electron 同源
   判定，**无需启动应用**。同类疑难症状应优先用它排除。`Add-Type` 在本机被安全策略
   拦截，走不通。
