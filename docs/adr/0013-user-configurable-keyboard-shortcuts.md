# ADR 0013: 用户可改键盘快捷键

## Status

Accepted(2026-09-19)

## Context

窗口内此前没有任何快捷键设施：渲染层唯一的全局绑定是 DEV 期切换性能浮层的
`Ctrl+Shift+D`（`src/App.tsx:99-107`）；Daemon 与 Sidecar 只讲 Companion
REST/WS，不做键盘分发（`src-tauri/src/companion/server.rs:406-437`）；Electron
壳没有原生菜单栏也没有 `globalShortcut`，只有托盘菜单
（`desktop-electron/src/main.ts:352-368`）。因此「命令」这一层并不存在——动作散落
在各组件自己的点击处理里，既列不出来，也无法统一绑定。

三个宿主（Electron 桌面壳、PC 浏览器、移动浏览器）共享同一份渲染层，移动端没有物
理键盘；内置浏览器面板的焦点在网页里，渲染层的 keydown 收不到。

参考实现 PI-Desktop（`packages/shared/src/keyboard-shortcuts.ts`）用一份纯函数模型
加单个 `window` keydown 服务 16 条命令，其关键不变量是「可绑定键位必须带修饰键或为
F1–F12」，因此不需要「焦点在输入框里就禁用快捷键」这类守卫。

## Decision

1. **引入 Command 与 Shortcut 两个领域概念**，命令目录是应用内置的单一真值源：稳定
   id、分组、中文标题、出厂默认键位（含 macOS 专用默认）。用户只改键位，不改目录。
   首版 9 条：后退、前进、新建会话、打开设置、搜索会话/命令、折叠侧边栏、展开/折叠侧面板、
   停止生成、聚焦输入框。
2. **键位是可读字符串**，修饰键规范写法为 `Mod+Ctrl+Alt+Shift`；`Mod` 表示 macOS 的
   Cmd 与其余平台的 Ctrl，展示时才渲染成 ⌘ 或 Ctrl。
3. **匹配按物理键 `event.code`，不按 `event.key`**——与键盘布局无关，且 Option+I 这类
   死键不会误判。
4. **键位覆盖是三态**：无覆盖（用出厂默认）/ 字符串（自定义）/ 显式解绑（`null`）。
   出厂默认只在读取时合并、从不物化落盘；取值等于出厂默认的覆盖不携带用户意图，保存
   时丢弃。
5. **可绑定键位必须带至少一个修饰键，或为 F1–F12**。录制时同时拒绝保留键位（复制、
   粘贴、全选、撤销、重做、刷新、回车发送、关闭窗口等平台与编辑语义键位）以及与其他
   Shortcut 的冲突。不做自动让路，也不做冲突对话框。
6. **分发是渲染层单点**：App 根挂唯一一个 `window` 冒泡期 keydown，依次跳过纯修饰键、
   IME 组合中的按键（`isComposing` / `keyCode 229`）与**已经被焦点组件消费掉的按键**
   （`event.defaultPrevented`，例如 composer 的 Enter、终端里的 Ctrl+B），再按目录顺序取
   首个命中，`preventDefault` 后执行。不做作用域引擎，也不在分发点判定「焦点是否可编辑」。
7. **键位覆盖是配置，落在 Daemon 的 `config.json`**（`GET/PATCH /api/config`），随所有
   Daemon Client 一致，而不是 localStorage。
8. **命令目录同时供 ChatSearchDialog 的「命令」分区使用**，并在搜索项、设置页和
   `TooltipHint` 中显示键位标签——键位必须能被发现。
9. **首版不做系统级（应用外）全局快捷键**，不动 Electron 壳与托盘。
10. **接受宿主差异**：桌面壳里全部命令生效；PC 浏览器宿主里属于浏览器 UI 级的组合（新窗口、
    地址栏/搜索栏聚焦、书签栏、下载页等）网页拦不到，这些键位在该宿主自然不可用。不为
    此分叉默认键位，但设置页的快捷键分区必须明示这一点。

## Considered Options

- **只读快捷键一览表（不可改键）**：否决。价值集中在可改键与冲突检测上，只读表收益极低。
- **组件各自监听 keydown**：否决。优先级不可控，同一个键会被多个组件重复拦截。
- **分发时做作用域判定**（活动视图 / 活动面板 / 是否可编辑 / 是否有对话框）：否决。用
  「必须带修饰键」这一条不变量替代；作用域引擎会引入五维上下文与难以测试的分支，而它
  保护的场景（裸键）本就不允许被绑定。
- **两态解绑（删除覆盖即恢复默认）**：否决。用户无法表达「我不要这个快捷键」，删除与
  解绑语义混淆。
- **键位覆盖写 localStorage**：否决。与其余设置分裂，浏览器宿主与桌面壳会不一致。
- **键位用 `event.key` 匹配**：否决。布局相关，非 US 布局与中文键盘会错配。
- **独立命令面板浮层另立入口**：否决。与已有的 ChatSearchDialog 重复，命中率不如把命令
  并进搜索。
- **首版做系统级全局快捷键（隐藏/唤回窗口）**：否决。需要动壳层与托盘，Windows 上部分
  组合还需 Rust 低级键盘钩子，收益不足。
- **多段 chord（如 `Mod+K Mod+S`）与整包键位预设**：首版不做。增加录制、冲突与展示的复
  杂度，需求未验证。
- **给当下不在界面上的命令绑键位**：首版目录里曾包含「折叠/展开预览面板」与「折叠/展开文
  件树」，它们指向的 `PreviewPanel` / `FileTree` 目前没有任何挂载点（右侧面板走的是
  `SidePanel`，它用的是另一套 `DiffView`）。给不可见的组件绑键位是假功能：它占住键位、出现
  在设置页与搜索结果里，却什么都不做。两条命令已摘除，等这些面板接回界面再加。
- **为浏览器宿主单独调整默认键位，或同一命令分两套默认**：否决。会让「默认键位」变成宿主
  的函数，模型、设置页与文档都要分叉；浏览器宿主是次要入口，不值得为它牺牲桌面壳的手感。

## Consequences

- 快捷键功能不动 Daemon 协议，只在 `AppConfig` 上新增一个键位覆盖字段；渲染层是唯一分发
  点，因此桌面壳与浏览器宿主共享同一套键位与同一份行为，移动端因无物理键盘自然不参与；
  但浏览器宿主里浏览器自身保留的组合（新窗口、地址栏聚焦等）拦不到，两宿主因此只能部分
  一致；具体哪些组合被吞随浏览器与平台而变，未逐条验证。
- 「必须带修饰键」意味着在 composer 里按带修饰键的组合也会触发命令（例如 `Mod+K` 打开
  搜索）。这是有意的取舍，因为裸键不可能被绑定。
- 内置浏览器面板聚焦时快捷键不生效（焦点在网页上），这与「输入框内仍生效」的差异需要在
  文档与设置页文案里说清。
- 保留键位表是硬编码清单，不查平台 API；平台新增保留组合需要手动维护。
- 键位展示依赖平台判定，而渲染层此前没有平台助手（只有
  `src/components/settings/AboutSettings.tsx:189-202` 的零散 userAgent 判断），本 ADR
  顺带引入唯一的平台真值源。
- 若将来要做系统级快捷键，需另行决策（壳层注册 + Windows 特殊组合的钩子），不影响本
  ADR 的三态与目录模型。
- `Mod+K`（搜索）在设置视图里是空操作：搜索对话框渲染在侧边栏内部，而设置视图把侧边栏换成
  了设置导航。这好过「在设置页按了没反应、回到会话视图却凭空弹出搜索框」；离开会话视图时
  侧边栏卸载会把开合状态收掉。
