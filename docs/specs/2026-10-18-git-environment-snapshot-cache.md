# 环境信息快照缓存（Git Environment Snapshot Cache）

**Status:** implemented

## Problem Statement

摘要面板的「环境信息」（变更增删统计 + 当前分支）在每次面板重新挂载时都会重新拉取 `getRepositoryState` + `getStatusChanges`，在 daemon 侧各触发约 5 个和 3 个 git 子进程。窄档摘要以浮层呈现，浮层每次开关都会卸载/重挂，于是反复开关摘要、切换项目、钉住/取消钉住都会重复同一份工作，即使仓库毫无变化。

## Solution

把环境信息快照提升为按项目键控的应用级缓存。摘要面板（浮层与内联面两种面）都从该缓存读取：

- 同一个项目第二次打开摘要时，直接显示上次的快照，不再触发任何 git 调用（首次或未缓存的项目才显示加载占位）。
- 切换项目首次访问该项目时拉取一次，其他项目的缓存保留。
- 在会改变环境信息的操作之后异步刷新对应项目：分支检出/新建成功后、以及一个回合结束（settle）后。
- 仓库不是 git 仓库时的「取不到仓库」兜底状态同样被缓存，避免反复重试。

## User Stories

1. 作为 CodeMUX 用户，我希望重新打开摘要时环境信息立刻出现，以便不为没有变化的数据看一次加载骨架。
2. 作为 CodeMUX 用户，我希望反复开关窄档摘要浮层时复用缓存数据，以便不为无谓的重复付 git 代价。
3. 作为 CodeMUX 用户，我希望浮动浮层与钉住的内联摘面共用同一份缓存，以便在两种展示档位间切换时不触发重载。
4. 作为 CodeMUX 用户，我希望切换到另一个项目时该项目只取一次环境信息，以便每个项目的数据正确且不必重取其他项目。
5. 作为 CodeMUX 用户，我希望切回先前访问过的项目时保留其缓存的环境信息，以便返回项目是即时的。
6. 作为 CodeMUX 用户，我希望在摘要里检出或新建分支后分支名与变更统计刷新，以便立刻看到正确的分支。
7. 作为 CodeMUX 用户，我希望一个回合结束时环境信息自动刷新，以便变更统计反映智能体刚做过的事，而不用我手动重开面板。
8. 作为 CodeMUX 用户，我希望进行中的对话显示上一次已结束回合的统计、而不是回合中途实时更新，以便面板在一回合内保持开销低。
9. 作为 CodeMUX 用户，我希望不是 git 仓库的项目显示同样的兜底文案且不被每次打开重查，以便兜底状态稳定且开销低。
10. 作为 CodeMUX 用户，我希望同一项目的两次并发打开被去重为一次在途请求，以便快速开关不会扇出成重复的 git 调用。
11. 作为 CodeMUX 用户，我希望快速切换项目时较早访问的慢响应永远不覆盖较新的响应，以便显示的环境信息始终对应当前项目。
12. 作为 CodeMUX 维护者，我希望取数路径集中在一个 store 而不是每个组件一个 hook，以便取数/刷新策略只有一个落点。
13. 作为 CodeMUX 维护者，我希望刷新触发点明确且少（项目切换、分支操作、回合结束），以便行为可预期、不在每次渲染或每次打开时重取。
14. 作为 CodeMUX 维护者，我希望这个 store 有就近的单元测试，以便缓存/刷新/去重语义无需渲染即可测试。
15. 作为 CodeMUX 维护者，我希望现有摘要面板组件测试断言「第二次打开不再取数」，以便缓存契约不会被悄悄破坏。

## Implementation Decisions

- 新增一个 zustand store（仓库对共享状态的既有约定），按项目路径键控环境信息快照。每个条目的形状为：仓库状态、统计（`additions`/`deletions`）、加载态（`loading` / `ready` / `unavailable`）、可选的不可用文案、以及取数时间戳。
- 动作/接口：
  - `ensure(projectPath)` —— 该项目没有缓存条目时才取数；用于挂载 / 项目变化。
  - `refresh(projectPath)` —— 总是重新取数并替换；在途期间保留上一份数据可见（不闪骨架）。
  - 同一路径的请求串行化：在途 `ensure` 被后续 `ensure` 共享；在途期间到来的 `refresh` 不被丢弃，而是排在当前请求之后补取一次（连续的多个 `refresh` 合并为一次）。这样「刚打开面板的首次取数」不会吞掉「回合结束的刷新」。
  - 一个 `cancelled` / 代数守卫，使过期响应不能覆盖较新项目的快照（沿用当前 hook 已有的守卫）。
- 消费方：共享的摘要面板正文改为读 store，而不是组件本地 state。两张面（浮动浮层正文与钉住的内联面）渲染同一个 store 支撑的正文，因此档位切换复用数据。
- 刷新触发点（恰好这三个）：
  1. 项目切换 → `ensure(path)`（新路径只取一次，其他条目保留）。
  2. 分支检出 / 新建成功 → `refresh(path)`（替代今天本地的 `reload()`；这是显示分支正确的必要条件）。
  3. 回合结束 → 订阅 agent store 的 `isRunning` 由 true→false 的边沿（先例：`agentStore.ts` 现有的 `useAgentStore.subscribe`），解析受影响的项目路径，异步 `refresh(path)`。
- 本次不引入 TTL，也不引入手动刷新控件（明确后置）。
- 陈旧策略：回合进行中快照可以陈旧，回合结束时对账刷新。这是刻意的，对齐参考实现「结算而非实时更新」的取舍。
- 不改动 daemon：本 spec 继续使用现有的两个 RPC（`getRepositoryState`、`getStatusChanges`），不新增 daemon 端点、不改 schema。

## Testing Decisions

- 好的测试只断言外部行为：给定一个项目，跨挂载/打开发生了多少次取数、显示了什么、什么会触发重取——绝不断言内部 state 布局。
- store 单元测试（新增，就近）：
  - `ensure` 取一次并复用；
  - 新路径上的 `ensure` 会取数；
  - `refresh` 会重取；
  - 在途去重把并发调用收敛为一次；
  - 过期响应守卫忽略乱序响应；
  - `unavailable` 兜底被缓存。
- 组件测试（更新现有）：扩展摘要面板组件测试，断言第二次打开渲染缓存值且不再产生额外 `daemonFacade.git` 调用；断言一次分支检出恰好触发一次刷新；断言项目变化触发一次取数。
- 先例：`src/hooks/useRepoBranch.ts` 已实现「按路径键控缓存 + 在途去重」的模式（含 TTL），`GitEnvironmentPopover.test.tsx` / `SummaryPanelSurface.test.tsx` 已 mock `daemonFacade.git`——两者都作为模板复用。

## Out of Scope

- daemon 侧把 `getRepositoryState` + `getStatusChanges` 合成一次 `git status` 的「单快照端点」（ZCode 有，本 spec 后置为后续票）。
- daemon 侧文件监听驱动的自动刷新（CodeMUX 没有文件监听；回合结束触发是可移植的等价物）。
- 让审查面板（`ReviewPanel`）复用这份缓存。
- 基于时间的 TTL 以及任何面向用户的手动刷新控件。

## Further Notes

- 已研究的参考实现：`D:\project\ZCode`——它把单个 `useGitRepository` 提升到应用根，用「workspace 变化 / pane 打开 / 显式刷新令牌」的判定门控真实 git 工作，并对文件监听驱动的刷新施加 60s 防抖，以避免 agent 批量写文件时的 git I/O 风暴。本 spec 只引入其中两个想法：**单点提升的状态**与**仅在相关变化时刷新**；监听器与合并 RPC 有意不引入。
- 保留摘要 hook 已有的 `cancelled` / 过期响应保护，因为面板会在两张面之间切换挂载点，且项目可被快速切换。
