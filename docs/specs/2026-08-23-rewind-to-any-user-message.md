# 对话回退至任意用户消息(Rewind to Any User Message)

> labels: `ready-for-agent`
>
> 日期:2026-08-23
> 参考实现:paseo 的 rewind 能力模型(能力声明 + 统一回退入口 + provider 各自实现)

## Problem Statement

当用户发现早期某条指令方向不对、或想让对话从更早的位置重来时,目前只能回退最后一轮("回退并编辑这条消息"按钮只出现在最新一条用户消息上)。对于更早的历史用户消息,用户没有任何入口可以回到那个节点,只能放弃整个会话重新开始,或者用 Fork 从 assistant 消息分叉出一个新会话——但 Fork 会产生新会话,不满足"在当前会话里就地回退"的诉求。

## Solution

参考 paseo 的设计,把现有"回退最后一轮"泛化为"回退到任意历史用户消息":

1. 每一条已完成的用户消息在 hover 时显示回退入口。
2. 点击后,该消息及其之后的全部内容被移除——前端事件流截断,provider 原生历史(Claude/Codex 的会话 JSONL、OpenCode 的 SQLite)同步截断。
3. 被回退的用户文本自动填回输入框,供编辑后手动重发;输入框已有草稿时不覆盖。
4. 会话运行中或只读时拒绝回退,行为与现状一致。

Claude/Codex 的后端定位逻辑已支持任意目标,本需求以前端泛化为主,外加补齐 OpenCode 后端只能按最新一轮截断的缺口。文件恢复(checkpoint)类能力不在本期范围。

## User Stories

1. 作为桌面端用户,我希望 hover 任意一条历史用户消息时看到回退入口,以便我能从任意历史位置重来。
2. 作为桌面端用户,我希望点击某条历史用户消息的回退按钮后,这条消息及其后的所有内容从界面消失,以便会话干净地回到该节点之前的状态。
3. 作为桌面端用户,我希望回退的同时 provider 侧的原生会话历史也被同步截断,以便后续对话不会携带已被移除的上下文。
4. 作为桌面端用户,我希望被回退的那条文本自动填回输入框,以便我直接修改措辞后重发。
5. 作为桌面端用户,我希望输入框里已有未发送草稿时,回退不覆盖我的草稿,以免丢失正在输入的内容。
6. 作为桌面端用户,我希望回退操作完成后由我自己决定何时重发,以便我有机会改写甚至放弃这条消息。
7. 作为桌面端用户,我希望会话正在运行时回退入口不可用并给出提示,以避免中断进行中的任务产生不确定状态。
8. 作为桌面端用户,我希望只读会话不支持回退,以保证导入/共享会话的完整性语义不被破坏。
9. 作为桌面端用户,我希望对刚发出、provider 尚未确认的消息不能回退,以避免定位失败导致历史损坏。
10. 作为桌面端用户,我希望回退到第一条用户消息时会话变为空会话状态,以便我从头开始当前主题。
11. 作为桌面端用户,我希望最新一条用户消息仍保留现有的"编辑并重发"交互,以便高频场景的操作路径不变。
12. 作为 Claude 会话用户,我希望回退任意历史轮次后继续对话时,Claude 能基于截断后的历史正确响应。
13. 作为 Codex 会话用户,我希望回退任意历史轮次后继续对话时,Codex 线程与界面显示保持一致。
14. 作为 OpenCode 会话用户,我希望同样获得任意历史位置的回退能力,而不是只有最新一轮。
15. 作为用户,我希望回退失败时看到明确的错误提示,且原有会话内容不受破坏,以便我可以安全地重试或放弃操作。
16. 作为用户,我希望回退后 token 用量、待办列表、变更文件等派生面板状态一并刷新,以免看到已被移除内容的残留信息。
17. 作为使用过 Fork 功能的用户,我希望回退与 Fork 并存互不影响:回退作用于当前会话,Fork 从 assistant 消息分叉出新会话。
18. 作为中文界面用户,我希望回退相关的提示文案为中文,并与现有文案风格一致。
19. 作为开发者,我希望三种 agent kind 走统一的回退命令通道和目标定位契约,以便后续接入新的 provider 时只需实现同一定位协议。

## Implementation Decisions

- **复用现有回退命令通道**:不新增 Tauri 命令,沿用现有 rewind 命令及其 `RewindTarget` 定位契约(provider_message_id 优先,line_index、turn_ordinal + text_fingerprint 兜底)。
- **Store 泛化**:将"回退最后一轮"的 store action 泛化为接受目标用户消息索引的形式;旧签名保留为薄包装(始终解析到最后一条可回退用户消息),现有调用点无感迁移。回退成功后的派生状态清理集合(streaming、todos、用量、变更文件等)整体沿用。
- **定位强度门槛**:仅当目标用户消息具备强定位标识(provider 原生消息 ID)时才允许任意历史回退;乐观渲染、尚未拿到 provider 确认标识的消息一律禁用入口。这对应 paseo 的 "provider 未确认前禁止 rewind" 校验。
- **运行中拒绝**:isRunning 时直接拒绝(返回空结果并提示),不做先中断再回退。这是与 paseo 的有意差异,已确认。
- **回填语义**:回退成功后仅当输入框为空时填入被回退文本(paseo 同款 only-if-empty 策略);最新一条消息保留现有 assistant-ui 编辑(onEdit)即"回退后立即以编辑内容重发"的行为,两者并存。
- **OpenCode 后端补齐**:将 OpenCode 的回退从"只支持最新一轮"(按最新用户消息时间删除)扩展为按 RewindTarget 定位——先用 provider 消息 ID 在消息表查出目标行时间戳,再以其为界执行既有的级联删除事务。Claude/Codex 的 JSONL 截断路径零改动(其任意目标定位已存在并通过原子写保证崩溃安全)。
- **能力静态映射**:建立 AgentKind → 回退能力(conversation / files / both)的静态声明表,本期 UI 只消费 conversation 位;files/both 留给二期,避免二期再动 UI 结构。这与 paseo 的 capability 驱动菜单思路一致,但采用编译期静态表而非运行时探测(CodeMUX 三种 runtime 能力已知且固定)。
- **UI 形态**:用户消息行 hover 显示撤销图标按钮,带工具提示;菜单顶部展示警告文案("此消息之后的内容将被移除");点击期间进入 pending 态防重复提交。样式遵循仓库 UI 规范(动态字号工具类、共享 TooltipHint、既有 ui 组件库优先)。
- **错误处理**:后端失败原样透传错误消息,前端 toast 展示;由于截断是原子替换(临时文件 + rename / 单事务),失败不会留下半截历史。

## Testing Decisions

- 只测外部行为,不测内部实现细节:断言"点击后事件流截断到目标之前""命令收到什么定位参数",不断言内部中间变量。
- 完全复用现有三层接缝,不新建接缝:
  1. **组件层**:assistant-ui 运行时挂载测试(现有回退用例的同一挂载方式),覆盖入口出现条件(历史消息可见、最新消息维持编辑语义)、运行中/弱定位禁用、点击触发的 store 调用参数。
  2. **Store 层**:agent store 单测,复用"回退最后一轮"既有用例模式,新增任意索引回退、强/弱 locator 分流、read-only 与 running 拒绝、回填 payload 组装等用例。
  3. **Rust 层**:JSONL fixture 单测沿用现有内嵌测试风格(临时文件构造多轮历史),补充 OpenCode SQLite fixture 用例验证按 target 截断的删除边界(目标行本身及之后全删,之前的 tool_result 归属关系不破坏)。
- 先例参照:组件层与 store 层各有现成回退测试可直接模仿;Rust 层 rewind 模块内嵌了十余个 JSONL 定位/截断测试,OpenCode 新用例与其并列放置。

## Out of Scope

- 文件恢复(files / both 回退模式):依赖各 provider checkpoint 能力,涉及 sidecar 参与回退执行,单独立项。
- 运行中自动中断再回退:本期保持拒绝语义。
- Git 分支创建与工作区隔离:Fork 功能已有的同类边界继续适用。
- 移动端(src-mobile):桌面端先行,移动端跟随既有 parity 计划另行安排。
- Fork 行为调整:两者语义不同(就地回退 vs 分叉新会话),互不改動。

## Further Notes

- 本 spec 由 paseo 回退功能调研驱动:paseo 采用"统一入口 + capability 声明 + provider 各自实现(fork/rollback/树导航)"的委托式架构;CodeMUX 因直管 provider 原生存储(JSONL/SQLite),选择继续沿用"存储截断"路线,仅在产品形态与防护语义上对齐 paseo(provider ack 门槛、only-if-empty 回填、能力驱动 UI)。两条路线的关键分岔点(是否引入 sidecar 参与回退执行)推迟到文件恢复二期再决策。
- 回退与 Fork 的组合语义:回退不影响 session_lineage 关系;若父会话在被子会话引用期间发生回退,子会话拥有独立 provider 历史,不受影响。
