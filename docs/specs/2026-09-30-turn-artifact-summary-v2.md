# Turn 级产物汇总 v2：跨 Agent Kind 的解析统一

**Status:** ready-for-agent

**Supersedes:** [2026-09-01-turn-artifact-summary.md](2026-09-01-turn-artifact-summary.md)（该文档的「工具识别（MVP 白名单）」与「OpenCode 隔离」两节已与实际实现和现状不符，本次一并作废）

## Problem Statement

用户在一个 Session 里与某个 Agent Kind 协作时，需要在一轮结束时一眼看清「这轮到底产出了什么文件」。CodeMUX 已经把这个能力做成时间线上的产物卡片，但它今天只对一部分 Agent Kind、一部分写文件路径成立，而且同一个 Turn 在不同时刻可能给出不同的数字。

具体地，用户会遇到以下相互独立的问题。

**覆盖不全。** Claude Code 的批量编辑工具（一次改多个位置）在卡片上完全不存在——单次编辑会显示，批量编辑消失，用户看到的是随机漏报。OpenCode 的主要写文件工具同样不计入。pi 这个 Agent Kind 从头到尾没有产物卡片，用户切换 Agent Kind 后会觉得这个功能时有时无。

**数字会变。** 同一个 Turn 的 +N/−M 在刚跑完时和刷新页面后可能不一样，因为在两条管道上存在两套独立的行数计算实现，它们对「文件末尾有没有换行」的判定相反。实测在真实数据上有 6.1% 的条目分歧。

**一轮可能挂出多张卡。** 一条 User Message 换来六张各说各话的产物卡片是实际发生过的，用户无法判断「这轮」的产物到底是哪一张。

**参数后到导致静默丢失。** 某些运行时先发工具调用、后补参数，而当前实现只看第一帧，于是这些写文件操作永远不会出现在卡片上。

**老 Session 无法追溯原因。** 持久化时间线里只留下过两类写文件工具，且 pi 从未写入过任何 summary，因此历史轮次的缺口无法通过重算补回——这一点必须写明，以免后续误以为「换个算法就能修复老数据」。

## Solution

让「一个 Turn 一张产物卡片」对所有 Agent Kind 都成立，并且数字在实时与刷新后一致。

做三件事，且只做这三件事：

1. **把「工具调用 → 产物条目」的解析从各自为政改成统一规则。** 规则只描述行为：识别哪些工具算写文件、从工具入参里怎么找文件路径、怎么把一次成功的调用折算成一条产物条目，以及基线怎么绑定。规则同时落地在 sidecar（跑实时）与 Daemon（跑历史加载）两侧，由一份共享 fixture 锁住两端一致。
2. **把轮次边界统一成一条 User Message。** 一条 User Message 换来的整轮回复只挂一张卡片，位置在该轮最后一条助手消息之后。这与「一轮」在产品语义上一致：用户发一句话，agent 干完活。
3. **让两端行数计算采用同一语义。** 明确「文件末尾换行的有无不算一次变更」，消除同一 Turn 出现两个数字的可能。

**卡片本身的外观、文案与交互沿用现状**：折叠态一行「N 个文件已更改」加增删徽章，展开态是文件行（图标、文件名、路径、增删数），点击文件行在侧栏打开该文件的 diff。不新增分组、不改文案、不新增状态徽章或颜色标记、不新增第二个动作按钮。

## User Stories

### 产物卡片的基础体验

1. 作为一个用户，我希望一条 User Message 换来一张产物卡片，以便不必在回复中间判断哪张卡片代表这一轮。
2. 作为一个用户，我希望产物卡片挂在该轮最后一条助手消息之后，以便它语义上属于「这轮工作的结果」。
3. 作为一个用户，我希望卡片默认折叠并只显示「N 个文件已更改」加增删徽章，以便长对话不被产物列表撑开。
4. 作为一个用户，我希望展开卡片后看到每个文件的名字、路径与增删行数，以便快速评估改动规模。
5. 作为一个用户，我希望点击某个文件行能在侧栏打开它的 diff，以便审查具体改动。
6. 作为一个用户，当某轮没有任何成功的文件变更时，我希望不显示卡片，以便界面保持简洁。
7. 作为一个用户，我希望卡片在我刷新页面或重新打开 Session 后与实时时完全一致，以便不怀疑自己记错。

### 跨 Agent Kind 覆盖

8. 作为一个 Claude Code 用户，我希望单次编辑文件出现在卡片上，以便知道这轮改过什么。
9. 作为一个 Claude Code 用户，我希望一次批量修改多个位置的编辑也出现在卡片上，以便不漏掉最大宗的改动。
10. 作为一个 Claude Code 用户，我希望新建文件出现在卡片上并计入增行数，以便知道这轮产出了哪些新文件。
11. 作为一个 Codex 用户，我希望通过补丁方式修改的文件出现在卡片上，以便覆盖 Codex 的主要写文件路径。
12. 作为一个 OpenCode 用户，我希望通过补丁方式修改的文件出现在卡片上，以便覆盖 OpenCode 的主要写文件路径。
13. 作为一个 OpenCode 用户，我希望写入与编辑操作继续出现在卡片上，以便不因新逻辑而回退。
14. 作为一个 pi 用户，我希望 pi 的编辑与写入操作出现在卡片上，以便四个 Agent Kind 的体验一致。
15. 作为一个 pi 用户，我希望 pi 的批量编辑（一次改多个位置）折算成同一文件的一条条目，以便不因 pi 的入参形状而漏报。
16. 作为一个用户，我希望同一个 Session 内切换 Agent Kind 后，每种 Agent Kind 的轮次各自独立汇总，以便不串线。
17. 作为一个用户，我希望在桌面、PC 浏览器与移动浏览器上看到同样的产物卡片，以便换设备查看时不丢失信息。

### 轮次边界

18. 作为一个用户，我希望 agent 在一轮内多次往返（读文件、改一批、再读、再改）仍然只产生一张卡片，以便「一轮」的概念与我的提问对齐。
19. 作为一个用户，我希望轮次边界是一条 User Message 而不是运行时内部的每次收尾，以便产物不被切碎。
20. 作为一个用户，我希望同一文件在这一轮内被多次修改时，卡片只反映这一轮开始到结束的净变化，以便卡片上的数字与点开的 diff 自洽。
21. 作为一个用户，我希望某一轮因我的中断而提前结束时，仍能看到轮内已经成功完成的变更，以便知道 agent 在我叫停前做了什么。
22. 作为一个用户，我希望某一轮失败时行为与中断一致，以便失败轮次的已落盘改动不被隐藏。
23. 作为一个用户，我希望排队消息在真正成为下一轮之后才开启新的产物汇总，以便产物归属不串到错误的提问上。

### 数据准确性

24. 作为一个系统维护者，我希望只有执行成功的写文件调用才计入产物，以便卡片可信。
25. 作为一个用户，我希望同一文件在同一轮内被多次写入时，基线取这一轮首次看到的文件内容，以便 diff 覆盖整轮变化而不是最后一步。
26. 作为一个用户，我希望工具调用参数分多帧到达时仍能正确统计，以便不出现「工具卡片显示了、产物卡片没显示」。
27. 作为一个系统维护者，我希望变更前的基线按精确路径匹配，以便不把改动记到另一个同后缀文件上。
28. 作为一个系统维护者，我希望从工具入参里递归地找文件路径（包括嵌套在 `input` / `arguments` / `params` / `payload` 之下的形状），以便不同 Agent Kind 的表达差异不需要逐个打补丁。
29. 作为一个系统维护者，我希望工具名归一化先查显式别名表、再用模式兜底匹配，以便 agent 上游改名时不静默漏报。
30. 作为一个系统维护者，我希望模式兜底匹配到的工具仍然必须解析出文件路径才计入，以便不把参数恰好含路径的非写文件工具误算成产物。
31. 作为一个用户，我希望卡片上的增删行数与点开的 diff 内容一致，以便两者不互相矛盾。
32. 作为一个系统维护者，我希望「文件末尾换行的有无」不算一次变更，以便尾随换行不产生虚假的 +1/−1。
33. 作为一个用户，我希望某一轮内净变化为零的文件不显示在卡片上，以便不出现「改了 0 行」的噪音条目。
34. 作为一个系统维护者，我希望新建、修改、删除的操作类型被记录在产物事件里备用，以便将来能区分它们而不必再改数据管道。
35. 作为一个用户，我理解本轮新建但行数为零的产物（例如图片）不出现在卡片上，以便卡片专注于文本改动。

### 双实现一致性

36. 作为一个系统维护者，我希望实时管道与历史加载管道用同一套解析规则，以便刷新前后数字不打架。
37. 作为一个系统维护者，我希望这套规则由一份跨语言的共享 fixture 锁定，以便两侧漂移在测试阶段就被发现而不是在生产里。
38. 作为一个系统维护者，我希望共享 fixture 覆盖行数计算的边界情形（空文件、仅换行、尾随换行、CRLF 与 LF、空行结尾），以便两端语义差异无处藏身。
39. 作为一个系统维护者，我希望共享 fixture 覆盖各 Agent Kind 的工具名与入参形状（含批量编辑、补丁、参数分帧到达），以便新增 Agent Kind 时有明确的对照基准。
40. 作为一个系统维护者，我希望 fixture 同时是「期望行为」的唯一定义，以便两端测试都不再各自维护一份期望值。

### 持久化与历史

41. 作为一个用户，我希望产物事件继续进入 Session 的 CodeMUX Event 序列并被持久化，以便刷新后仍可见。
42. 作为一个用户，我希望产物事件在轮次边界处发出，以便前端能按轮挂载。
43. 作为一个系统维护者，我希望历史加载路径在缺少产物事件时能按同一规则合成，以便导入的旧 Session 也有卡片。
44. 作为一个系统维护者，我希望产品理解写清楚：历史轮次缺的产物无法通过换算法补回，因为持久化时间线里根本没有对应的工具事件，以免后续做无收益的迁移。
45. 作为一个用户，我希望本次改动不改变我已打开的历史 Session 的既有卡片内容，以便不出现「同一段历史前后长得不一样」。

### CLI 原生会话同步（第三条路径）

46. 作为一个用户，我希望我在 CodeMUX 之外用 CLI 直接跑出来的会话，被同步进来后也有产物卡片，以便不区分会话是怎么来的。
47. 作为一个用户，我希望从 CLI 同步进来的历史会话，其产物卡片的覆盖范围与实时跑出来的会话一致，以便同一个 Agent Kind 不因来源不同而少统计。
48. 作为一个系统维护者，我希望工具名匹配严格大小写不敏感，因为 CLI 同步路径保留上游原始拼写（有的 Agent Kind 大写开头，有的全小写），以便同步来的会话不会整体失效。
49. 作为一个系统维护者，我希望认识到 CLI 同步路径**不产生任何变更前快照**，因此退化基线对同步来的轮次是常态而非边缘情况，以便不把退化路径写成「极少走到」的分支。
50. 作为一个系统维护者，我希望任一逻辑操作（单次编辑、批量编辑、写入、补丁三类）在「实时形状」与「CLI 同步形状」下都被同一套规则识别，以便两条来源不产生覆盖差异。
51. 作为一个系统维护者，我希望 Codex 的两条来源都被覆盖：实时是文件变更项（带结构化差异），同步是自由文本补丁，以便 Codex 产物在实时与刷新后都在。
52. 作为一个系统维护者，我希望补丁解析对「自由文本补丁」与「结构化变更数组」两种输入都成立，因为同一逻辑操作在两条来源下携带着不同的载荷。

### 库与文档

53. 作为一个系统维护者，我希望删除从未被读写的产物表，以便 schema 不再携带死结构。
54. 作为一个系统维护者，我希望该表的删除通过既有迁移模式完成并带测试，以便升级路径可验证。
55. 作为一个系统维护者，我希望本决策以新文档记录并把旧 spec 标记为被取代，以便保留「当时为什么这么定」的历史。
56. 作为一个系统维护者，我希望把本次的事实核查证据（各 Agent Kind 的真实工具名与入参实测、真实数据里的多卡片实例、两端行数分歧的量化、CLI 同步路径的形态差异）落成研究笔记，以便后续不再重复调研。
57. 作为一个系统维护者，我希望文档索引同步更新，以便下一个人能找到这些结论。

## Implementation Decisions

### 术语与轮次定义

本 spec 中「一轮」（Turn）指**一条 User Message 换来的一整轮回复**，即产品语义上的轮次。它与运行时内部每完成一次往返就收尾一次的边界**不是同一件事**：一条 User Message 之下，运行时可产生多次内部收尾。统一后的轮次边界是「下一条 User Message 到达」或「Session 结束」。

这条定义不是新造的：前端的 Turn 切分已经是按 User Message，历史合成路径已经按同一基准切分，本次要改的是 sidecar 实时路径的收尾时机。

### 解析规则层（唯一需要跨语言复制的部分）

规则层的职责边界固定为五件事，两侧各自实现、行为必须逐字节一致：

1. **工具识别**：先查显式别名表归一化工具名，命名风格差异（大小写、连字符、下划线、括号、`mcp__<server>__` 前缀）都要塌缩到同一规范名；未命中别名表时用模式兜底匹配写文件语义；兜底命中的工具仍必须解析出文件路径才计入。**匹配一律大小写不敏感**（见下节「三条来源路径」的硬约束）。
2. **路径提取**：递归下钻工具入参，穿透 `input` / `arguments` / `params` / `payload` 这类嵌套壳（深度设上限），接受多种路径字段拼写（含 notebook 类路径字段）；同时支持从补丁正文里解析被操作的文件。
3. **操作类型**：把一次调用归类为新建、修改或删除。该归类只写入产物事件备用。
4. **基线绑定**：按精确路径匹配变更前快照；缺快照时退化为由编辑片段自身拼出的前后文本。**这条退化路径不是边缘分支**：CLI 同步来的轮次一律没有快照，pi 的实时轮次也没有。退化路径必须与快照路径同等对待（同等测试覆盖）。
5. **行数计算**：按换行切分并**丢弃末尾空行**后比较，使「文件末尾换行的有无」不构成变更。两端必须采用这一语义。

### 三条来源路径（兼容性硬约束）

工具事件有三条来源，同一逻辑操作在不同来源下携带**不同的名字形态与载荷形状**。规则层必须对三者同时成立，否则会出现「实时有卡片、刷新后没有」或「CLI 同步进来的会话整段没有卡片」。

| 来源 | 工具事件从哪来 | 工具名形态 | 变更前快照 |
|------|---------------|-----------|-----------|
| **实时** | 各 Agent Kind 的运行时规范化器 | 部分被小写化，部分原样透传 | Claude Code 与 OpenCode 有；pi 没有 |
| **CLI 原生会话同步** | 从各原生存储重建后进入同一规范化管线 | **保留上游原始拼写与大小写** | **一律没有** |
| **库内既有时间线** | 直接读持久化的事件行 | 取决于写入当时 | 视当年而定 |

三条硬约束：

1. **大小写不敏感是正确性要求，不是风格偏好。** CLI 同步路径原样透传上游工具名：某个 Agent Kind 用大写开头，另一个全小写。任何基于工具名的判断若丢掉大小写归一，**会让整条同步来的会话失效**。
2. **快照缺失是常态。** 变更前快照由实时运行时钩子产生；原生日志里不存在这种东西，所以 CLI 同步路径**不可能**产生它。实现时不得把「有快照」当作主路径、「无快照」当作降级容错。
3. **同一操作的多形状必须都认。** 典型例子是补丁类操作：实时来源是结构化的变更数组（每项带路径与差异文本），同步来源是一整段自由文本补丁。**两者都要能被同一套规则解析。** 只实现其中一种，就会造成「跑的时候有、刷新后没有」这类分叉。

### 汇总器：跨帧参数与轮次累积

汇总器当前有两个结构性缺陷，都在本次修复范围内：

- **参数分帧到达**：某些运行时先发出不带参数的工具调用帧，参数随后补上。汇总器改为按工具调用标识累积入参，并在工具收尾时重试绑定基线，而不是只信任第一帧。
- **轮次累积**：汇总器的清空时机从「每次运行时内部收尾」改为「下一条 User Message 到达」或「Session 结束」。同一轮内首次建立的文件基线在整轮内保持，最终条目反映该轮开始到结束的净变化。

同文件在同轮内多次成功修改时，**保留最后一次成功修改的结果**（不累加各次增删数）。这是对「净变化」语义的直接实现，也是与点开 diff 自洽的前提。

### 前端挂载

前端**不做汇总**，只做挂载与渲染。现有的挂载条件已经覆盖完成、中断与失败三种 Turn Outcome，无需改动；把多个产物事件按文件取最新再挂到该轮最后一条助手消息的逻辑也已经存在，本次只需补回归测试把它钉住。

卡片组件的生产代码本次不动。

### 双实现与共享 fixture

两侧实现共用一份仓库内的共享 fixture 文件，两个测试套件都从仓库根按相对路径读取。fixture 分两部分：

- **行数用例**：`名称 / 变更前 / 变更后 / 期望增 / 期望删`
- **事件序列用例**：`名称 / cwd / 事件序列 / 期望产物条目`

两端断言同一份期望值。任何一端与 fixture 不一致即为失败——包括那些「看起来更合理」的差异（例如把尾随换行算作变更）。

### 库变更

- 旧 spec 头部标记被本 spec 取代，正文不改。
- 新建研究笔记记录本次事实核查证据与「不该迁移历史数据」的推导。

## Testing Decisions

### 什么算好测试

只断言外部行为：给定一组 wire 级的 CodeMUX Event 序列，断言汇总器产出的产物条目形状与内容；给定一对文本，断言增删行数。不断言内部 Map、不断言函数名、不断言实现顺序。

不测 UI 像素。前端只补一条回归测试证明「一轮一张卡片、挂在该轮最后一条助手消息上」。

共享 fixture 是期望值的唯一定义处：两端测试都不自己写期望数字。

### 接缝

| 接缝 | 层级 | 测什么 | 不测什么 |
|------|------|--------|----------|
| 解析规则 + 汇总器（两侧，共享 fixture） | 最高 | 工具识别、路径提取、操作类型、基线绑定、行数语义 | 真实进程、真实磁盘、真实 diff 视图、数据库 |
| 各 Agent Kind 的运行时适配 | 中 | 每个 Agent Kind 一轮只发一个产物事件、发在轮次边界、无变更时不发 | 算法本身 |
| 前端挂载 | 中（复用既有） | 一个产物事件 → 该轮末尾一张卡片；完成/中断/失败三种收尾都成立 | 卡片视觉细节 |
| 数据库迁移 | 低 | 旧表被移除 | 其他 schema 行为 |

**明确不采用**「真实 sidecar 进程 + 真实 agent + 真实文件」的端到端接缝：它是最贵的接缝，且**无法**证明两种语言实现一致——那只能靠共享 fixture。

### 共享 fixture 必覆盖的场景

fixture 的组织原则：**按「逻辑操作」分组，每组都要有「实时形状」与「CLI 同步形状」两个用例。** 这是本次最容易漏掉的一维——只照实时帧写 fixture，同步路径就会成为漏网。

**行数语义**（语言间必须逐字节一致）：空到空；空到无尾随换行的一行；空到有尾随换行的一行；仅在末尾增删换行；追加一行（有/无尾随换行）；去掉末尾换行；CRLF 完全相同；CRLF 与 LF 文本相同；LF 与 CRLF 互转；末尾增删空行；仅含换行的输入；含 BOM 的相同内容。

**工具识别**：每个 Agent Kind 真实工具名的典型拼写与常见变体拼写；补丁类工具；批量编辑类工具；被明确排除的读文件与终端类工具；不认识但形似写文件的名字（验证兜底规则与「必须解析出路径」的约束）。**大小写变体必须成对出现**：同一规范名的大写开头形态与小写形态各一例，用以钉死「匹配大小写不敏感」这条硬约束。

**路径提取**：顶层路径字段；嵌套在 `input` / `arguments` / `params` / `payload` 下的路径字段；补丁正文中的多文件路径；相对路径按 cwd 解析。

**一次调用的折算**，每个逻辑操作两套形状：

| 逻辑操作 | 实时形状 | CLI 同步形状 |
|----------|---------|-------------|
| 写入新文件 | 工具调用入参含完整内容，无快照 | 重建的工具事件入参含内容，无快照 |
| 写入已存在文件 | 有变更前快照 | 无快照（退化为空基线） |
| 单次编辑 | 有快照，验证前后文本与行数 | 无快照，验证由编辑片段拼出的前后文本 |
| 批量编辑 | 入参含多个编辑片段，无快照 | 同形状，但工具名可能不做小写化 |
| 补丁类操作 | 入参是结构化变更数组（每项带路径与差异文本） | 入参是一整段自由文本补丁（可能含多个文件） |

补充用例：补丁的新增、更新、删除三态；同文件多次修改取最后一次；失败的工具不计入；参数分帧到达。

**轮次累积**：同一轮内多次往返只产出一个产物事件；事件落在该轮收尾之前；无成功变更时零产出；下一条 User Message 开启新的汇总。

- 前端产物事件的解析测试与挂载测试（已覆盖完成与中断）

## Out of Scope

- **历史轮次的产物回填**。持久化时间线里只有过两类写文件工具、且 pi 从未写入过 summary，新规则要解析的那些工具事件在历史数据里根本不存在，重算无法补回任何条目；重建还可能因缺失变更前快照而降低部分老轮次的精度。老轮次保留现状。
- 跨 Turn 或跨 Session 的产物总账、项目级产物台账。
- 卡片视觉结构改版：新建与改动分组、标题文案调整、状态徽章、按状态着色、第二个动作按钮。
- 卡片上的「打开文件」动作。
- 产物的已读、忽略、撤销、批量保存等交互。
- 统计终端命令对文件的改动（shell 或终端工具内嵌的写文件）。
- 以 git 或磁盘状态作为产物事实来源、以及任何轮次边界的工作区快照与对比。
- Notebook 专用编辑路径的产物统计（归一化表保留 notebook 路径字段，但本次不为该类工具定义折算规则）。

- 移动伴侣新增编辑能力（仅继承时间线渲染）。

## Further Notes

### 本次不改变的可观察行为（产品确认）

以下几点看起来像缺陷，但经确认保留现状，写在这里以免后续被当成 bug 修掉：

- **净变化为零的文件不显示**：某轮内净变化为零的文件不出现在卡片上。代价是「本轮新建但行数为零」的产物（典型是图片）不可见。
- **操作类型不驱动界面**：新建、修改、删除会被写入产物事件，但卡片不据此改变任何展示。
- **点击文件行打开 diff**：卡片上的文件行仍只提供在侧栏打开 diff 一个动作。

### 已确认的现状偏差（本次不做，但记录在案）

- 某些运行时会先发不带参数的工具调用帧，参数随后才到。修复后这类调用会计入，但**修复前已经发生过的**那部分调用不在本次回填范围内。
- 持久化事件的顶层字段形状存在多种来源（实时持久化与历史导入各自补不同的信封字段）。这不影响前端排序与去重（走数据库列而非 JSON 字段），本次不动。

### 待实测佐证的空白（诚实记录）

**Codex 的产物覆盖目前只有代码路径证据，没有生产数据佐证。** 事件投影的两条来源都已确认成立：实时来源把文件变更项投影为补丁类工具调用（带结构化的变更数组），CLI 同步来源把上游的自定义工具调用投影为同名的补丁类工具调用（补丁正文嵌在入参的嵌套字段里），两侧解析路径也都已存在。但在本机时间线数据库中，补丁类工具在持久化的工具事件里出现 **0 次**——该库覆盖的时间段内没有走过 Codex 补丁路径的会话。因此实现完成后的验收必须**主动构造一次真实 Codex 补丁改动**来确认，不能只依赖单元测试。

### 工具名归一化在当前代码里有三处，覆盖各不相同

这是「同一个工具在一张卡上认、在另一张卡上不认」的结构性来源，值得记录：

| 位置 | 用途 | 覆盖 | 特点 |
|------|------|------|------|
| sidecar 汇总器 | 产物汇总 | 写入 / 编辑 / 补丁 | 纯小写比较，无别名表 |
| Daemon 合成器 | 产物汇总（历史加载） | 同上 | 纯小写比较，与上一处互为手抄 |
| 前端工具卡片 | 工具卡片标题与参数摘要 | 读 / 写 / 编辑 / 终端 / 检索 / 任务等十余项 | 保留大小写；批量编辑与 Notebook 编辑靠**上游恰好发来那个大小写**才命中，小写形态会掉到兜底 |

本次统一的是前两处（产物链路）。前端那处服务于工具卡片显示，与产物汇总不是同一关注点，本次不动——但如果将来再出现「工具名认不认」的争议，应先看这三张表的覆盖差异，而不是各自再加一条判断。

### 相对旧 spec 的关键差异

旧 spec 把「批量编辑、Notebook 编辑、终端内嵌补丁」列为首版明确排除项，并声明 OpenCode 继续使用其原生 summary、不接入统一汇总器。这两条都已与现状不符：统一汇总器实际上已接入 OpenCode，而 OpenCode 的原生 summary 已被主动停用。本 spec 同时补上旧 spec 完全未提及的 CLI 原生会话同步路径。本 spec 取代这两条决定。

### 双实现是本次的核心风险

实时管道在 sidecar（TypeScript），历史加载管道在 Daemon（Rust），两者必须对同一输入给出同一输出。共享 fixture 是唯一的防线，因此它的覆盖范围应当被当作长期资产对待：新增 Agent Kind、新增来源路径、或上游工具改名时，**先补 fixture 再改实现**。fixture 的每一组用例都要问一次「另一条来源长什么样」。
