# 连续思考与工具的 Activity Run 折叠分组

> labels: `ready-for-agent`
>
> 日期: 2026-11-14
>
> 状态: 已实现并通过自动化门禁（vitest 3083+、tsc、build、build:web）；工单 01–07 完成，工单 08 的 dev:desktop 手工验收矩阵待执行（docs/tickets/activity-run-collapsible-groups/，01–08）
>
> 范围: Claude Code、Codex、OpenCode、pi；主会话与子智能体只读时间线

## Problem Statement

当前主会话与子智能体时间线会把连续思考和工具调用逐条平铺。虽然展示层已经能识别连续的 Activity Run，但普通过程段没有组头和段级折叠；长任务中，读取、搜索、终端、修改、电脑控制与思考会连续占据大量纵向空间，用户很难快速找到助手正文，也难以把握一段工作的当前进度与整体规模。

四个 Agent Kind 的事件封装方式不同：同一过程可能被拆成多条消息，也可能把思考与工具放在同一条消息中；OpenCode 还可能用多个事件刷新同一次工具调用。若直接按消息数量或 provider 字段分组，会造成不同 Agent Kind 的展示不一致、重复计数或顺序错误。

实时过程还有额外复杂性：未提交的思考先进入独立流式缓冲区，工具结果会回填既有工具卡，正文、问询和委派又各自拥有独立展示语义。折叠不能藏起需要用户处理的请求，不能改变消息顺序，也不能在流式追加或完成时覆盖用户已经做出的展开/收起选择。

现有“精简 AI 输出”提供整轮折叠，但它只解决“每轮只保留最终总结”，不能替代普通模式下的连续过程整理。聚合标题目前还会根据子项失败显示警示，用户希望失败信息只留在具体工具条目上，不再向各种聚合标题冒泡。

## Solution

在现有 Activity Run 纯展示投影上恢复并完善**连续过程折叠组**。思考与普通工具调用按真实可见顺序混入同一段，两个可见步骤起才形成折叠组；单个步骤维持现有行展示。分组不改写 CodeMUX Event、assistant-ui 消息或四个 Agent Kind 的适配器。

实时运行时组也默认折叠。组头优先显示最近仍在活动的工具或思考，没有活动项时显示最后一个可见步骤；段闭合后改为“探索 / 执行 / 修改 / 其他”的分类统计。修改按去重文件数统计，混合组不额外统计思考段数，纯思考组显示思考段数，组头不显示耗时。

可见正文、Interactive Request 和 Task/Agent 委派不被吞入普通折叠组。正文与待处理请求切断当前段；委派继续使用现有独立活动卡。用户手动展开或收起后，流式追加、段完成、切换会话、尾部窗口卸载以及整轮折叠都不得覆盖该选择；状态只在应用运行期间保留，重启后恢复默认折叠。

“精简 AI 输出”继续拥有整轮折叠。展开整轮后，内部仍按 Activity Run 分组，形成清晰的两级折叠。子智能体只读时间线使用同一套分组规则，但不因此获得 Composer、回退或其他主线程能力。

失败状态只保留在具体工具条目上。Activity Run 组头、整轮“已处理”和其他过程聚合标题不显示失败图标、失败计数或失败文案，也不因失败自动展开。

## User Stories

1. As a 桌面用户，我希望连续思考和工具调用合并为一个工作过程组，以便长任务不会用大量过程行淹没助手正文。
2. As a 桌面用户，我希望思考与工具按实际发生顺序混合排列，以便理解 agent 为什么执行下一步，而不是按类型重排过程。
3. As a 桌面用户，我希望只有两个及以上可见步骤才形成折叠组，以便一次简单调用不会多出一层无意义的交互。
4. As a 桌面用户，我希望同一条助手消息中的“思考 + 工具”也按两个步骤处理，以便不同 Agent Kind 的事件封装差异不会改变最终展示。
5. As a 桌面用户，我希望工具结果只回填原工具卡而不切断分组，以便连续调用不会被结果事件拆成许多小段。
6. As a 桌面用户，我希望可见助手正文切断当前过程组，以便正文的叙述层级和真实顺序始终清楚。
7. As a 桌面用户，我希望不同 Turn 和 User Message 不进入同一过程组，以便每段工作都归属于正确的对话轮次。
8. As a 桌面用户，我希望权限审批、Plan Approval 和问题作答始终独立可见，以便默认折叠不会让我漏掉需要处理的操作。
9. As a 桌面用户，我希望 Interactive Request 前后的过程分别成组，以便待处理卡片在文档顺序中保持明确位置。
10. As a 桌面用户，我希望 Task/Agent 委派继续使用独立活动卡，以便查看子智能体状态和打开详情的入口不被普通分组吞掉。
11. As a 桌面用户，我希望实时过程组默认收起，以便运行中也能保持对话紧凑。
12. As a 桌面用户，我希望折叠组头显示最近仍在运行的工具或流式思考，以便不展开也能知道当前正在做什么。
13. As a 桌面用户，我希望没有活动项时组头回退显示最后一个步骤，以便并发工具状态下仍有确定、可理解的摘要。
14. As a 桌面用户，我希望尚未提交的实时思考也能加入尾部过程组，以便思考提交前后的视觉结构连续。
15. As a 桌面用户，我希望实时思考从缓冲区转为已提交事件时不重复、不跳动、不换序，以便流式提交不会造成视觉闪烁。
16. As a 桌面用户，我希望流式正文一出现就闭合前面的过程组，以便“正在处理”的摘要不会覆盖已经开始回答的正文。
17. As a 桌面用户，我希望完成后的组头显示工具分类统计，以便快速回顾这一段做了多少探索、执行、修改和其他操作。
18. As a 桌面用户，我希望读取、搜索和网页工具归入“探索”，以便统计语义不受具体 Agent Kind 工具名影响。
19. As a 桌面用户，我希望终端、JS、浏览器和电脑控制归入“执行”，以便各类操作型工具使用统一口径。
20. As a 桌面用户，我希望写入、编辑和补丁工具归入“修改”，以便快速识别这段过程改变了文件。
21. As a 桌面用户，我希望计划、技能、待办和未识别 MCP 工具归入“其他”，以便未知工具不会破坏连续分组或从统计中消失。
22. As a 桌面用户，我希望同一文件被多次编辑只计一个文件，以便“修改”数字表达实际影响范围而不是编辑次数。
23. As a 桌面用户，我希望无法识别路径的修改仍按调用计数，以便统计不会漏掉修改，也不会伪造文件数。
24. As a 桌面用户，我希望混合组不显示思考段数、纯思考组显示思考段数，以便标题在信息量和长度之间保持平衡。
25. As a 桌面用户，我希望过程组头不显示耗时，以便避免与整轮“已处理”的耗时重复。
26. As a 桌面用户，我希望手动展开后新步骤追加时仍保持展开，以便我可以持续阅读完整过程。
27. As a 桌面用户，我希望手动收起后新步骤追加时仍保持收起，以便界面不会违背我的选择反复展开。
28. As a 桌面用户，我希望我手动展开的组在完成时也保持展开，以便完成事件不会打断正在查看的详情。
29. As a 桌面用户，我希望切换会话、离屏卸载或折叠整轮后返回仍记住我的组展开状态，以便临时导航不会丢失阅读上下文。
30. As a 桌面用户，我希望重启应用后分组恢复默认折叠，以便本地不会积累大量历史 UI 状态。
31. As a 桌面用户，我希望展开组后看到全部步骤摘要，并可继续单独展开某条思考或工具详情，以便分层控制信息密度。
32. As a 桌面用户，我希望组展开后随主页面完整滚动，以便不必在嵌套滚动区之间来回切换。
33. As a 桌面用户，我希望轻量组头和步骤缩进沿用现有对话风格，以便新分组不会变成层层嵌套的重卡片。
34. As a 开启“精简 AI 输出”的用户，我希望整轮仍默认只保留最终总结，以便现有设置语义不变。
35. As a 开启“精简 AI 输出”的用户，我希望展开整轮后内部仍按连续过程分组，以便两级折叠各自承担清晰职责。
36. As a 桌面用户，我希望失败只显示在具体工具上，以便聚合标题保持简洁，同时仍能展开定位真实问题。
37. As a 桌面用户，我希望工具失败不会强制展开过程组，以便错误不会突然改变我的阅读位置或覆盖手动选择。
38. As a Claude Code 用户，我希望历史与实时工具/思考使用新分组，以便原生消息拆分方式不会导致平铺刷屏。
39. As a Codex 用户，我希望工具生命周期与推理事件使用同一分组规则，以便 app-server 的不同事件形态仍得到一致展示。
40. As an OpenCode 用户，我希望同一次工具调用的 pending/running 刷新只算一个步骤，以便步骤数和分类统计不翻倍。
41. As a pi 用户，我希望思考与工具按统一可见步骤投影分组，以便第四 Agent Kind 不需要单独维护一套 UI。
42. As a 查看导入或只读 Session 的用户，我希望历史消息也按同样规则分组，以便旧对话同样易读且不需要重新运行 agent。
43. As a 查看子智能体详情的用户，我希望只读时间线也使用相同分组，以便从主对话进入详情后不会又回到平铺过程。
44. As a 子智能体详情用户，我希望面板仍保持只读，以便分组改造不会引入第二套输入、审批或回退入口。
45. As a PC 或移动浏览器用户，我希望主对话自动获得相同分组行为，以便统一前端在不同宿主上的信息密度一致。
46. As a 长会话用户，我希望新增分组不会让所有历史行随流式事件重渲染，以便信息密度优化不以掉帧为代价。
47. As a 长会话用户，我希望折叠、窗口增长和消息导航继续保持正确的滚动锚点，以便阅读位置不会因新容器而跳动。
48. As a 正在回看历史的用户，我希望新消息到达时不会被强行拽到底部，以便实时摘要更新不破坏回溯阅读。
49. As a 键盘或读屏用户，我希望组头是带展开状态和可访问名称的原生按钮，以便不依赖鼠标也能操作并理解摘要。
50. As a 使用暗色主题、自定义字号或窄屏的用户，我希望组头与步骤遵循既有设计 token，以便分组在所有外观设置下保持可读。
51. As a 系统维护者，我希望分组只是 UI 投影，以便 CodeMUX Event、Daemon、Sidecar 和消息转换语义完全不受影响。
52. As a 系统维护者，我希望四个 Agent Kind 共用分类与统计规则，以便新增工具时只维护一份映射，而不是四套展示分支。
53. As a 系统维护者，我希望保留现有稳定消息身份与过程组边界，以便工具详情、footer、回退、Fork 和窗口化不会因重挂而回归。
54. As a 系统维护者，我希望主会话和子智能体沿用现有产品测试接缝，以便用外部可见行为证明一致性，而不是新增一套脆弱测试入口。

## Implementation Decisions

### 1. Activity Run 是纯 UI 投影

- Activity Run 表示同一 Turn 内一段连续的可见思考与普通工具步骤，不是新的领域实体，不进入 CodeMUX Event、SQLite、Companion 协议或 assistant-ui 消息模型。
- 继续复用现有 Activity Run 构建入口，在其上补足分类统计、活动摘要与折叠所需的派生数据。不得把视觉合并下沉到事件转换器，否则会影响绝对事件下标、footer、Rewind、Fork 和消息身份。
- 段身份继续由 Turn 与段首事件稳定派生。流式追加必须复用同一段身份；不能因数组重建或尾部窗口重新挂载而改变。
- 主会话和子智能体时间线消费同一套段投影、分类和统计函数。两者可以保留各自的线程壳与视口，但不得各写一份分组规则。

### 2. 按可见步骤成组，而不是按消息或事件条数

- 每个非空思考块是一个可见步骤；每个实际渲染的普通工具调用是一个可见步骤。
- 同一工具身份因 pending、running、参数补全或结果回填产生的重复投影只算一步。缺少工具身份时，以实际可见工具卡为准，避免 OpenCode 双帧和类似刷新造成重复计数。
- 一个 Activity Run 至少包含两个可见步骤才显示为折叠组。单步骤段直接渲染现有思考行或工具行，没有组头，也不写入组展开状态。
- 同一条助手消息可以同时贡献多个步骤，因此“思考 + 工具”即使只有一个事件也满足成组门槛。
- 空思考、空正文、工具结果、原始诊断、流式增量、Turn Outcome，以及其他本来就不会产生可见行的事件，不贡献步骤，也不单独切断分组。不画行的判定与消息转换分派互为镜像并默认走白名单：只有真用户消息、转得出消息部分的助手事件、问询与 `visibleEventKinds` 系统事件会产出可见行，其余 kind（`file_snapshot`、`todo_list`、`permission`、`system`、`ready`、`done`、`mcp_status` 等）一律不断段——Claude Code 每次文件修改后都会发一个 `file_snapshot`，把它当行会把连续编辑切成一个个小段（线上实测：108 步回合被切成 15 段）。
- 段内步骤总数与展开后实际可见步骤行数必须一致；分类统计可以再按规则去重，但不能与工具身份去重口径相冲突。

### 3. 连续性边界

| 内容 | 是否进入普通 Activity Run | 是否切断当前段 | 展示方式 |
|---|---:|---:|---|
| 非空思考 | 是 | 否 | 组内思考步骤 |
| 普通工具调用 | 是 | 否 | 组内工具步骤 |
| 工具结果与参数刷新 | 不新增步骤 | 否 | 回填既有工具卡 |
| 可见助手正文 | 否 | 是 | 独立正文，始终可见 |
| User Message / Turn 边界 | 否 | 是 | 现有用户行与新 Turn |
| Interactive Request | 否 | 是 | 独立待处理卡片 |
| Task/Agent 委派 | 否 | 是 | 现有子智能体活动卡 |
| 不画行的诊断或元数据 | 否 | 否 | 不进入时间线 |
| 独立可见的非工具错误/系统事件 | 否 | 是 | 保持现有独立展示 |

- “思考 + 正文”位于同一事件时，思考属于它所在的过程段，正文仍在该事件的消息行内独立可见并闭合此段；隐藏过程步骤时绝不能连带隐藏正文。
- Interactive Request 包括权限审批、Plan Approval 与 AskUserQuestion 等等待人类决策的请求。待处理期间不并入组；完成后仍保留独立位置，不 retroactively 并回前后任一过程段。
- 子智能体委派卡继续承载自己的运行状态、拓扑和打开入口。普通 Activity Run 不统计委派卡内的子步骤。

### 4. 默认折叠与手动状态机

- 满足成组门槛的段，无论历史、实时、成功完成、失败或中断，初始都默认折叠。不再采用“实时尾段默认展开”的旧规则。
- 新出现的独立段拥有自己的默认状态，不继承上一段的展开选择。
- 用户第一次操作某个组后，该组进入手动接管状态：之后的流式追加、工具状态变化、段闭合和 Turn Outcome 都不得自动翻转它。
- 组完成只改变标题从活动摘要切换为分类统计，不改变展开状态。
- 从未被用户操作的组保持默认折叠，因此也不存在“完成时统一自动收起”的额外跳转。
- 单步骤段变为多步骤组时使用默认折叠；之后继续追加不再重置其手动状态。

### 5. 实时折叠标题选择

- 段尚未闭合时，从后向前选择最近的活动步骤：流式思考，或处于输入流式、等待执行、运行中的普通工具。
- 找到活动步骤时，组头复用该步骤现有的单行摘要语义：工具显示动作名称与参数摘要，思考显示其实时尾摘要。不得另写一套 provider 特定文案。
- 没有活动步骤但段尚未闭合时，显示最后一个可见步骤摘要，以覆盖并发工具或状态暂时静默的情况。
- 段被正文、Interactive Request、委派、User Message、Turn 边界或 Turn Outcome 闭合后，标题切换为完成态分类统计。
- 组处于展开状态时，实时组头仍表达当前活动步骤；展开只控制步骤列表，不改变摘要选择规则。
- 组头不显示段耗时，也不运行段级秒表。

### 6. 未提交流式内容的归属

- 未提交思考只有在它属于当前运行 Turn 的尾部、且中间没有正文或其他段边界时，才作为当前尾 Activity Run 的附加可见步骤。
- 若已有尾段加上实时思考达到两个步骤，就形成或更新折叠组；若实时思考仍是唯一可见步骤，则维持现有单步骤行，不强行成组。
- 实时思考提交为正式事件时，缓冲区步骤与已提交步骤必须去重，段身份与文档顺序保持不变。
- 未提交正文不进入 Activity Run。正文一旦可见，当前段立即闭合，正文继续使用现有流式 Markdown 与 reveal 节流路径。
- 误路由到文本缓冲区的思考、重复正文和已提交思考副本继续沿用现有去重规则；本需求不重新定义这些判定。
- 实时摘要通过窄范围订阅更新，不能让全部历史消息行随每个 token 重渲染。

### 7. 完成态分类统计

统一使用四个类别，顺序固定为“探索 → 执行 → 修改 → 其他”，只显示计数非零的类别。文案采用动宾短句、全角逗号串接（对齐 ZCode）：例如“已探索 2 次，已执行 11 命令，已修改 1 文件”；纯思考组为“已思考 N 段”。

| 类别 | 工具范围 | 计数口径 |
|---|---|---|
| 探索 | 文件/Notebook 读取、目录列举、文件匹配、文本搜索、图片查看、网页搜索与网页读取 | 去重后的工具调用数 |
| 执行 | 终端与标准输入、JS/REPL、浏览器工具、电脑控制，以及明确属于执行控制的会话工具 | 去重后的工具调用数 |
| 修改 | 文件/Notebook 写入与编辑、批量编辑、补丁应用 | 去重文件数；无路径调用另行计数 |
| 其他 | 计划、待办、技能、未识别内置工具与第三方 MCP 工具 | 去重后的工具调用数 |

- 分类依据规范化工具身份，不依据中文显示名；内置 MCP 工具先还原内置工具段，第三方 MCP 未命中显式映射时一律进入“其他”。
- 未识别工具不会成为段边界。新增 Agent Kind 或工具别名时，只扩展统一映射，不在视图组件添加 Agent Kind 分支。
- 混合组中的思考不追加到统计标题；纯思考组显示“已思考 N 段”。没有可统计工具但含非空思考的多步骤组按纯思考组处理。
- 完成态标题不显示总步骤数，因为总步骤数已由分类统计替代；整轮“已处理”的总步骤数保持不变。
- 标题在空间不足时保持单行并截断，完整统计仍通过可访问名称或既有提示组件可获得，不换行撑高组头。

### 8. 修改文件去重

- 修改统计以工具实际参数和结构化结果中可可靠识别的目标路径为准，包括一次补丁触及多个文件的情况；不从自然语言摘要猜路径。
- 路径采用纯词法规范化后去重：统一分隔符，处理 `.` 与 `..`，保留 Windows 盘符、UNC、POSIX 根和相对路径语义；不要求目标文件在本机存在，也不访问文件系统。
- 同一文件的重复 Write/Edit 只计一次；不同路径即使文件名相同仍分别计数。
- 无法识别路径的修改按去重工具调用数补记为“已修改 N 次”，不虚构文件路径，也不把它们丢弃；与有路径的修改并存时合成一句（“已修改 N 文件、M 次”）。不显示“（路径未知）”——它对读者没有行动价值（2026-11-21 用户确认）。
- 子智能体活动卡内部的文件修改不合并进父普通 Activity Run 的修改统计。

### 9. 展开状态的所有权与生命周期

- 组展开状态和“用户是否接管”按会话身份与稳定段身份保存；子智能体时间线还需包含子智能体身份，避免不同轨道共用 key。
- 状态保存在应用运行期的 UI 状态中，独立于组件挂载生命周期。切换 Session、尾部窗口卸载、离屏渲染和整轮折叠都不能清除它。
- 切换“精简 AI 输出”只改变整轮外层显隐，不清除内部组的手动状态。
- 状态不写入 Daemon、SQLite、localStorage 或应用配置；应用重启后全部恢复默认折叠。
- 清理会话或子智能体运行期数据时可以同步清理对应条目，避免无界保留已删除会话的 UI 状态。

### 10. 与“精简 AI 输出”的两级关系

- 关闭“精简 AI 输出”：正文之间按本 spec 显示 Activity Run 折叠组。
- 开启“精简 AI 输出”：整轮外层仍按现有规则收起，只保留最终总结和整轮“已处理”开关；外层收起时内部过程组不可见。
- 用户展开整轮后，内部仍显示 Activity Run 组，而不是恢复旧的全平铺。
- 整轮开关继续显示原有耗时和总步骤数，不显示本 spec 的分类统计；两种统计服务于不同层级。
- 外层整轮状态与内层组状态独立，任何一层自动或手动变化都不得重置另一层的手动选择。

### 11. 失败只留在具体工具

- 工具卡继续保留现有失败、拒绝、非零退出和错误结果展示，详情内容及交互不变。
- Activity Run 组头不根据子项失败显示图标、颜色、计数、文案或屏幕阅读器补充提示，也不强制展开。
- 整轮“已处理”开关移除由子项失败派生的警示图标、异常文案与相应辅助播报；保留耗时、步骤数和展开状态。
- 其他过程聚合标题同样不派生子项失败标记。子智能体自身的生命周期状态不是“子工具失败冒泡”，仍按既有子智能体协议展示，不在本需求中删除。
- 独立可见的错误、Diagnostic Event 与 Turn Outcome 仍按现有规则展示；本需求只禁止把工具失败重复聚合到组标题，不隐藏独立错误事实。

### 12. 展开内容与视觉

- 段首承载唯一组头；同段后续消息只贡献步骤，不重复显示组头。收起时隐藏的是过程步骤，正文、footer、Interactive Request 和其他非过程内容仍按原规则可见。
- 展开组按源码顺序显示全部步骤摘要。单条思考与工具继续拥有自己的详情折叠，不因为组展开而自动展开全文、参数或结果。
- 展开区不设置最大高度，不创建内部滚动容器，不引入组内虚拟列表；主对话滚动条承担全部导航。
- 视觉采用透明轻量组头、现有语义图标和 chevron，步骤做轻微缩进。不得新增卡片背景、边框或左侧竖线。
- 样式使用现有颜色、动态字号、圆角和动效 token；不得写死颜色、绝对文字字号、字面量动效时长或新增连续装饰动画。

### 13. 四个 Agent Kind 与两个时间线消费者

- Claude Code、Codex、OpenCode、pi 继续汇入同一个 assistant-ui 消息投影和主线程，不建立四套分组组件。
- 四个 Agent Kind 的适配只发生在既有事件规范化、工具身份和流式状态字段上；视觉层只消费统一字段。
- 主会话的实时缓冲、历史恢复、导入与只读 Session 都使用相同段构建规则。
- 子智能体详情复用同一 Activity Run 组件和统计规则，但仍是只读面板，不承接 Composer、Rewind、Fork、消息导航或第二套审批。
- 桌面壳、PC 浏览器和移动浏览器共用主前端，主对话无需宿主分支；浏览器宿主需要重新构建 Web 产物才能看到变化。

### 14. 消息身份、性能与滚动

- 保留现有消息 id、绝对来源事件下标、`msg-N` 导航锚点和消息行测量契约。逻辑分组不得改变 DOM 中文档顺序。
- 保留现有过程组作为稳定子树边界的作用；不得为了视觉简化而删除边界，导致流式更新时单条工具详情被重挂。
- 新增组头所需派生字段必须纳入现有行绑定比较器，并维持“追加一个事件只更新相关行”的计数型性能不变量。
- 实时摘要更新只影响当前活动组头与必要的尾部内容；不得把整份活动状态表变化传播为所有历史行重渲染。
- 不新增第三方虚拟化依赖，不给组容器新增 `content-visibility`，不引入测量式高度缓存。
- 折叠/展开、窗口增长和正文闭合必须继续使用现有 pre-paint 滚动锚定与测量事务；用户贴底时才跟随最新，上翻后不被拽回。
- 收起或展开不得把组头本身跳离视口；流式活动摘要文本变化不得造成组头高度周期跳动。

### 15. 可访问性与既有消息能力

- 组头使用原生按钮，提供展开状态、控制区域和明确可访问名称；键盘 Enter/Space 与鼠标点击等价。
- chevron 和运行状态装饰不重复进入可访问名称；活动摘要与完成统计需要能被读屏获取。
- 消息 footer、复制、附件、文件/diff 打开、工具详情、Rewind、Fork、计划卡片与消息导航的既有行为不变。
- 组折叠不得改变复制内容所依据的原始消息，也不得把隐藏过程伪造成被删除的数据。

### 16. 对旧展示决策的取代关系

- 本 spec 取代旧“实时尾段默认展开”“段头显示耗时与总步骤数”“精简模式展开后平铺”的决策。
- 旧实现中为保障正确性而建立的规则继续有效：正文不被过程折叠隐藏、工具结果不切段、工具身份去重、委派独立、稳定组边界、行级渲染收窄和滚动锚定。
- 旧“子智能体不承接工具分组”的范围限制由本 spec 明确解除，但子智能体只读边界不变。
- 本需求不需要新 ADR：它不改变 Daemon 权威、事件协议或持久化架构，只是统一前端展示决策。

## Testing Decisions

### 好测试的标准

- 只断言用户可观察行为：组头是否存在、哪些步骤可见、摘要内容是什么、文档顺序是否正确、点击后状态如何变化、切换后选择是否保留、滚动是否跟随。
- 四个 Agent Kind 使用各自代表性事件夹具驱动同一主线程，而不是直接构造最终 DOM 或为每个 Agent Kind 测一套内部组件。
- 分类、统计和路径规范化可以用纯函数测试覆盖复杂组合，但产品验收必须至少通过主会话或子智能体消费者观察到结果。
- 性能回归使用已有计数与比值断言，不使用不稳定的毫秒阈值。
- 对“无组头、步骤平铺”的既有断言按新需求重写；不得为了保留旧断言而同时维护两种互相矛盾的展示。

### 接缝一：主会话运行时挂载

沿用现有主会话 assistant-ui runtime/thread 挂载测试，覆盖：

1. 四个 Agent Kind 的历史事件都能得到相同 Activity Run 结构，且没有 provider 专属组件分支。
2. 单步骤不成组；两个步骤成组；同消息“思考 + 工具”成组；工具身份刷新不重复计步。
3. 思考与工具混排时 DOM 文档序保持不变，工具结果、raw、streaming、result、file_snapshot 等不产出可见行的事件不切段。
4. 独立正文和“思考 + 正文”同事件都闭合段，正文始终可见；User Message 与 Turn 边界不串段。
5. Interactive Request 独立可见并切段；委派活动卡保留，左右普通段不合并。
6. 实时组默认折叠；最近活动项优先；无活动项时回退最后一项；段闭合后切换分类统计。
7. 未提交思考加入尾段，提交后不重复；未提交正文闭合段；既有流式思考与正文 data 契约保持。
8. 分类映射覆盖内置别名、内置 MCP、第三方 MCP 和未知工具；未知工具进入“其他”且不切段。
9. 探索、执行、其他按调用计数；修改按 Windows/POSIX/UNC/相对路径规范化去重；多文件补丁与无路径修改不漏计。
10. 混合组不显示思考计数，纯思考组显示段数，所有组头不显示耗时。
11. 手动展开/收起在流式追加、段完成、Session 切换、尾部窗口卸载与整轮折叠后保持；模拟应用运行期状态重置后恢复默认折叠。
12. “精简 AI 输出”关闭时显示过程组；开启时整轮先折叠，展开后内部仍有过程组；切换设置不清除组手动状态。
13. 失败工具本身仍有失败状态，Activity Run、整轮“已处理”和其他过程聚合标题没有失败派生标记，也不自动展开。
14. 单条工具与思考详情保持原有独立展开行为；整组没有内部滚动区。
15. footer、复制、回退、Fork、计划卡片、消息导航和只读 Session 行为不回归。
16. 现有行渲染计数、比较器完备性、尾部窗口、流式分段和滚动锚定测试继续通过，并新增与活动组字段相关的计数守卫。

### 接缝二：子智能体预览面板挂载

沿用现有子智能体 store fixture 和只读面板测试，覆盖：

1. 同一组思考/工具事件在子智能体详情中产生与主会话相同的分组、摘要和分类统计。
2. 实时与完成态的默认折叠、手动状态和正文边界与主会话一致。
3. 子智能体身份参与状态作用域，不同子智能体相同段 key 不串状态。
4. 面板保持只读，没有新增 Composer、审批、Rewind 或 Fork。
5. 现有贴底跟随、上翻释放、回到底部、空态、footer 和文件/diff 入口不回归。

### 纯函数与组件附属测试

- Activity Run 投影：步骤识别、边界、身份去重、活动项选择、runKey 稳定、实时尾部附加与闭合。
- 分类统计：工具别名、四分类、未知工具、计数顺序、纯思考回退、修改路径规范化与无路径修改。
- 组头组件：可访问名称、`aria-expanded`、单行摘要、键盘操作、窄屏和语义 token 外观契约。
- 整轮折叠组件：耗时与步骤数保留，失败图标、失败文案和失败辅助播报移除。
- 这些测试服务上述两条产品接缝，不形成第三个独立产品验收入口。

### 验证门禁

- 迭代期运行受影响的主线程、子智能体、Activity Run、工具部件与滚动测试，并包含依赖这些模块的上游测试。
- 完成门禁运行根目录完整 Vitest、TypeScript 构建与 Web 构建；本需求不涉及 Rust daemon 或 Sidecar，无需对应构建。
- 使用 `dev:desktop` 做真实渲染人工核对：四个 Agent Kind 的代表性历史/实时夹具、长短过程组、手动状态、两级折叠、子智能体、暗色主题、字号变化、窄屏与滚动锚定。
- 至少在一个 daemon 服务的浏览器宿主重新构建并核对主对话，确认统一前端产物包含新行为。

## Out of Scope

- 修改 CodeMUX Event、四个 Agent Kind 的 runtime 适配器、Daemon、Sidecar、SQLite 或 Companion 协议。
- 为 Claude Code、Codex、OpenCode、pi 分别实现一套消息分组 UI。
- 直接复制 ZCode 私有 React 组件或其协议适配层；只借鉴纯视图派生、活动摘要和分类统计的架构。
- 引入新的虚拟化库、测量式高度缓存、组内滚动或组内虚拟列表。
- 跨应用重启持久化每个组的展开状态，或把 UI 状态写入用户配置。
- 改变 Interactive Request 的审批流程、子智能体生命周期协议、工具详情内容和单条工具失败展示。
- 删除“精简 AI 输出”设置，或把整轮“已处理”替换为 Activity Run 分类统计。
- 将子智能体预览扩展到当前不支持的 Mobile Companion，或给子智能体只读面板增加输入与审批能力。
- 重设计消息 footer、Markdown、工具卡片详情、消息导航、Rewind、Fork 或 Plan Approval。
- 在本次需求中顺便重构事件转换性能、窗口化策略或流式 Markdown；只守住既有性能与行为不变量。
- 创建实现计划或实施工单；这些属于 spec 确认后的后续流程。

## Further Notes

- ZCode 的可借鉴点是：从不可变消息行派生连续摘要组、最近活动项优先、完成态分类统计、稳定组身份，以及展示层与数据层解耦。其组件与 codeMUX 的消息协议、窗口化和子智能体模型不同，不应直接复用。
- 本 spec 有意与 ZCode 保持几项差异：未知工具归入“其他”而不切段；手动状态在应用运行期跨挂载保留；展开组随主页面完整滚动；组头不显示耗时；失败不向聚合标题冒泡。
- 仓库旧版 Activity Run 曾采用实时展开、段头耗时与总步骤数，随后为精简输出移除普通段头。当前需求不是简单恢复旧组件，而是在保留后续正确性与性能修复的前提下，以本次确认的新状态机和统计口径重新引入组头。
- 尤其需要保留的既有修复包括：GroupedParts/Activity Run 稳定边界避免工具详情重挂；同工具身份去重避免 OpenCode 双帧翻倍；正文与思考同事件时正文永不随段隐藏；行级绑定比较器避免历史整体重渲染；长会话测量事务与 pre-paint 锚定避免折叠跳动。
- 本 spec 与 ADR 0003 相容：Activity Run 只是 CodeMUX Event 的另一种 UI 投影，不创建第二条权威时间线。
