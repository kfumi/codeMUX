# 电脑控制（Computer Use）

**Status:** ready-for-agent

## Problem Statement

用户在 CodeMUX 里只能让智能体读写文件、跑命令、改配置。遇到要操作图形界面的事，比如在这个网页上填完这张表、把报错截图里的现象复现出来、去系统设置里打开某个开关，只能靠用户自己动手，再把结果粘贴回来讲给智能体听。市面上有成熟的开源电脑控制驱动和浏览器自动化服务，但 CodeMUX 今天没有统一的暴露方式：内置浏览器只能人看不能让智能体动，桌面截图贴不进上下文，更没有受控的键鼠执行。用户要么自己当智能体的手，要么去别的应用里完成。
## Solution

在 CodeMUX 里增加一套分三级、默认全关的电脑控制能力，统一以系统内置 MCP 服务加操作规范 skill 的形态交给智能体。第一级让智能体操作侧边栏内置浏览器里的网页；第二级让智能体看桌面截图；第三级在用户显式开启后，让智能体经独立驱动进程操作操作系统界面。驱动的安装、检测、更新、诊断都在设置页一站式管理；哪些应用可操作由允许列表加内置拒绝列表决定，宿主自己永远不可操作；急停在进程级生效；每一步截图与动作都可回放。五个智能体通过现有 MCP 同步链路自动获得能力，不需要逐个改造。
## User Stories

### 浏览器级操作

1. 作为桌面用户，我希望智能体能读取当前浏览器页的结构化快照（编号截图加元素列表），以便智能体知道页面上有什么可点的东西。
2. 作为桌面用户，我希望智能体能按元素编号点击、输入、选择和滚动页面，以便我说句话就填完表。
3. 作为桌面用户，我希望每次浏览器操作前都看到审批提示，以便在误操作前拦下来。
4. 作为桌面用户，我希望审批支持单步放行和按会话记住两种粒度，以便高频操作不被弹窗淹没。
5. 作为桌面用户，我希望浏览器操作开关默认关闭，打开后智能体才获得能力，以便平时保持零风险。
6. 作为桌面用户，我希望元素定位失败时智能体自动重试并在超过次数后停下告诉我，以便点不准时不乱点。
7. 作为桌面用户，我希望支付、登录、密码类页面操作前必须人工确认，智能体不能代替我点，以便资金和账号安全。
8. 作为桌面用户，我希望上述能力不改变内置浏览器既有的证书、缓存与资料管理行为，以便新旧功能互不干扰。
### 驱动生命周期与可操作范围

9. 作为桌面用户，我希望在设置页看到驱动的安装状态与版本号并一键重新检测，以便知道电脑控制能不能用。
10. 作为桌面用户，我希望有新版本时收到提示并一键更新，且升级必须经过我确认，以便版本变化可控。
11. 作为桌面用户，我希望有一键诊断告诉我驱动在不在、权限够不够、链路通不通，失败项告诉我怎么修，以便出问题能自助排查。
12. 作为桌面用户，我希望有启动和急停按钮，急停直接杀驱动子进程，且按 Esc 能全局强打断当前操作，以便失控时两秒内停下来。
13. 作为桌面用户，我希望允许列表为空时表示除拒绝外全部可操作，逐行写应用名，保存后即时生效，以便按需收紧范围。
14. 作为桌面用户，我希望内置拒绝列表包含密码管理器、终端、锁屏、Windows 安全中心，以及 CodeMUX 自己、安装器和更新器，且删不掉，以便智能体永远碰不到这些地方。
15. 作为桌面用户，我希望智能体试图操作被拒绝的应用时被拦截，并在轨迹里记一笔，以便事后可查。
### 桌面观测与系统级执行

16. 作为桌面用户，我希望智能体经我批准后能截取桌面或活动窗口，以便智能体看得见报错现场。
17. 作为桌面用户，我希望在会话输入框旁点一下就能手动截一屏贴进上下文，以便不经过智能体也能给图。
18. 作为桌面用户，我希望只读截图默认走轻量确认、可按会话记住，而任何输入动作都走严格审批，以便安全和效率兼顾。
19. 作为桌面用户，我希望截图含密码框时自动打码或拒绝，且轨迹里的按键序列脱敏存储，以便隐私不进日志。
20. 作为桌面用户，我希望开启系统级执行后，智能体能按相对坐标点击、拖拽、滚动、按键、输入和等待，以便连原生应用也能操作。
21. 作为桌面用户，我希望高分屏和多屏下的坐标换算由执行器兜底，我不用管，以便点哪儿是哪儿。
22. 作为桌面用户，我希望默认有步数上限、单步超时、连续多步无变化自动停三条刹车线，以便死循环自己停。
23. 作为桌面用户，我希望所有输入动作在任何权限模式下都不豁免审批，以便 full-access 也管得住手。
24. 作为桌面用户，我希望弱模型下可配接地解析服务增强定位，以便点得准。
25. 作为桌面用户，我希望全程轨迹（每步动作加前后截图加模型理由）可回放，以便复盘和取证。
26. 作为桌面用户，我希望审计日志记下谁、何时、哪个会话、什么动作，以便事后可查。
### 多智能体可用性与交互

27. 作为 Claude 或 Codex 用户，我希望截图到定位到点击到验证的闭环直接可用，以便主力模型先跑通。
28. 作为 Gemini 用户，我希望电脑控制基本可用，复杂定位走界面元素语义兜底，以便同样受益。
29. 作为 OpenCode 或 Pi 用户，我希望按所配模型分级可用，弱模型至少界面语义操作可用，以便能力承诺与模型实际能力相符。（注：不做过度承诺，弱模型只保语义操作。）
30. 作为任一智能体的用户，我希望 MCP 工具返回的截图能被模型真正看到，以便能力不是摆设。
31. 作为任一智能体的用户，我希望某家的原生权限门拦截电脑操作时，界面明确告诉我是哪一家的门，而不是静默失败，以便我知道去哪儿开。
32. 作为桌面用户，我希望设置页有电脑控制分组：总开关、允许范围、步数上限，以便一处管完。
33. 作为桌面用户，我希望轨迹在消息流里渲染成步骤加缩略图加动作，可点开展示前后对比，而不是一堆 JSON，以便看得懂。
34. 作为桌面用户，我希望驱动掉线或被杀毒拦截时，界面降级为告诉我怎么手动点，而不是卡死，以便总有路走。
35. 作为浏览器或手机端用户，我希望至少能查看轨迹回放，以便不在桌面前也能复盘。
## Implementation Decisions

- 能力只暴露为一个系统内置 MCP 服务，配一条电脑控制操作规范 skill；五个智能体经现有 MCP 统一同步链路自动获得能力，不逐个写驱动。
- 权威归属：会话、配置、审批、审计归 daemon；Electron 壳只负责窗口内的浏览器执行与全局 Esc 热键；系统级执行由独立驱动子进程承载，daemon 管其生命周期，包括拉起、健康检查、更新与急停时杀进程。
- 第一级复用既有浏览器自动化接缝，在其上补结构化快照与元素级操作；不出浏览器、不碰系统键鼠。
- 第二级只读截图走独立只读工具集，与输入工具分权；坐标统一用相对值，分辨率换算收敛在执行器层。
- 第三级先用外部开源驱动做概念验证（子进程加标准输入输出 MCP 形态），自研只保留三处：内置浏览器、审批粒度、轨迹回放；分发前确认再分发合规。
- 传输约束：各智能体映射层当前只接受标准输入输出形态；集中托管若对外用远端传输需补垫片或扩展映射，验证阶段先用每会话子进程形态，治理收敛到 daemon 侧进程表。
- 审批复用既有三档权限模式与变更前确认界面，新增单步放行与按会话记住两种粒度；系统输入动作在任何模式下都不豁免；登录、支付、验证码、删文件、关防护等敏感场景强制人工确认。
- 拒绝策略：允许列表为空即除拒绝外全允许；内置拒绝含密码管理器、终端、锁屏、安全中心与宿主自身及安装更新器，不可删除。
- 截图隐私：按需拉取、逐条审计；密码框打码或拒绝；按键序列脱敏存储。
- 循环护栏：步数上限、单步超时、停滞检测写入执行器；提示词注入约束写进 skill，网页弹窗文字视为污染源，高危组合必须停下等人确认。
## Testing Decisions

- 好测试只测外部行为：给定快照返回元素操作、给定审批决策放行或拦截、给定步数上限停机，不测内部实现细节。
- 单元层面覆盖 MCP 工具参数校验、允许拒绝判定、审计脱敏、分辨率换算（覆盖常见缩放）。
- 既有接缝优先：浏览器自动化既有测试形态、MCP 同步既有测试、审批既有测试全部沿用并扩展。
- 概念验证验收（Claude 加 Codex 先行）：截图工具返回的图片能被模型看到并据此点击；元素级填表任务端到端通过；急停可快速杀停子进程。
- 系统级回归用 OSWorld 任务子集，不自造标准。
- 改动代码的就近测试加受影响测试先行，全套在提交前跑，与仓库既有测试纪律一致。

## Out of Scope

- 云端浏览器代操作服务接入（违背本地优先）。
- 给智能体裸终端命令执行能力（不可审计、风险不可控）。
- macOS 与 Linux 的系统级执行（本期只做 Windows；设计保留跨平台插槽）。
- 自研视觉接地模型（先用强模型直连加可选外部解析服务）。
- 移动端壳执行系统输入（移动端只做触发与回放查看）。
- 自动处理验证码、代替用户登录与支付。

## Comments

**驱动选型概念验证结论(2026-10-07,工单 05）：行,但分两步走。**

- **形态选对了**：外部驱动当 stdio MCP 子进程托管是可行的 —— daemon 拉起、握手、列工具、急停杀进程全部跑通（真实子进程测试，急停 1 秒内收敛）。协议面就是 MCP，不需要为驱动改 CodeMUX 的代码，换驱动只改一条命令配置。
- **坑位清单**：
  1. 内置 server 原先在进程启动时就要求 daemon 在跑，导致「daemon 没起时连工具面都看不到」。已改成端口/令牌调用时现取（顺带解决 daemon 重启换端口）。
  2. 会话 kind 与运行时回退不一致会让会话静默丢工具（`gemini_cli` 走 Claude 运行时却拿不到内置 MCP），注入判据必须问运行时而不是 kind 字符串。
  3. 驱动的升级通道没有通用解法：包管理器各不相同，所以做成用户配置的更新命令 + 强制确认，daemon 不猜。（2026-10-08 补充：cua-driver 本体自带 `update --apply` 自更新通道，更新命令留空即走它 —— 见工单 09；「daemon 不猜包管理器」的原则不变，猜的是驱动自己。）
  4. 第三方二进制分发合规未决：spec 既定「分发前确认再分发合规」，本次未下载任何第三方驱动，`driver_command` 由用户自行指向。
- **cua-driver 仍是第三级首选**（调研结论）：独立二进制 + stdio MCP + 自带版本/诊断的口径与本项目的 runtimes 托管机制同形。接它只需在设置里填驱动命令，代码侧无需改动。
- **仍未验证**：真实第三方驱动在真机上的截图/点击行为、Claude 与 Codex 的端到端闭环、OSWorld 子集分数。这些写在 `docs/research/2026-10-07-computer-use-capability-matrix.md` 的验收表里，由 dev 联调补齐。
