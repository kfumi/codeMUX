# Turn 级产物汇总事实核查（面向 v2 规格）

## 摘要

`docs/specs/2026-09-30-turn-artifact-summary-v2.md` 动工前，对「产物卡片的数据到底准不准」做了五项事实核查。结论全部基于实测，不基于代码推断：

1. **pi 的工具集与入参形状是已知的**：`bash` / `read` / `edit` / `write` / `ask_user_question`，没有批量编辑工具；`edit` 的入参形状**我们的解析器已经支持**。pi 缺的只是「没有挂汇总器」。
2. **OpenCode 的补丁工具确实在被使用**，且当前实现把它整个漏掉了。同时暴露一个独立缺陷：工具参数会分帧到达，第一帧不带参数。
3. **一条 User Message 挂出多张产物卡片是实际发生过的**，生产库中存在 1 条 User Message 对应 6 张卡片的会话。
4. **两套行数实现确实不一致**，实测真实数据分歧率 6.1%，根因是「文件末尾换行」的语义相反。
5. **Codex 的两条来源都已打通**，但缺少生产数据佐证；**CLI 原生会话同步路径可用，却对实现有两条硬约束**（工具名匹配必须大小写不敏感、变更前快照一律缺失），且原先的测试计划完全漏掉了这条来源。

另有三项核查过程中意外发现，其中一项直接否决了「重算历史数据」的方案。

## 核查方法

| # | 问题 | 数据来源 | 样本量 |
|---|------|----------|--------|
| 1 | pi 的写文件工具名与入参形状 | 本机 pi 原生会话 JSONL | 13 个会话，约 8 MB |
| 2 | OpenCode 的补丁工具入参字段 | 本机 OpenCode 会话数据库 | 20,337 条工具调用记录 |
| 3 | 「一轮多卡片」是否真实发生 | 本机 CodeMUX 时间线数据库 | 43 个含产物事件的会话 |
| 4 | 两套行数实现是否一致 | 跨语言对照实验 + 生产数据回归 | 18 个边界用例 + 560 条真实条目 |
| 5 | Codex 与 CLI 原生会话同步的兼容性 | 三方（sidecar / Daemon / 前端）的工具名归一化表 + 事件投影代码路径 | 全量静态核查 |

## 核查 1：pi 的工具名与入参形状

从 13 个真实 pi 会话中统计出现过的工具名：

```
1141  bash      91  read      71  edit      19  write      4  ask_user_question
```

**没有批量编辑工具。** pi 不提供这一类能力，因此 v2 的批量编辑覆盖只对 Claude Code 有意义。

实测入参形状（全部 71 条 `edit` 与 19 条 `write` 一致）：

| 工具 | 入参 |
|------|------|
| `edit` | `{path, edits: [{oldText, newText}, ...]}` |
| `write` | `{path, content}` |
| `path` 取值 | cwd 相对路径，例如 `apps/sidecar/src/piRuntime.ts` |

**结论**：`edit` 的批量形状（`edits[]` 配 `oldText`/`newText`）在现有解析代码里**已经被处理**，工具名归一化也已经能命中 `edit` / `write`。pi 的产物缺口是纯粹的**接线缺失**，不是解析能力缺失。

一个必须记录的副产品限制：**pi 从不发出变更前快照事件**。因此 pi 的产物条目只能走退化路径（由编辑片段自身拼出前后文本），在「同一文件被多次编辑」时精度低于提供快照的 Agent Kind。

## 核查 2：OpenCode 的补丁工具

从 OpenCode 会话数据库统计：

```
7447 read   4765 bash   3631 grep   2434 edit   976 glob   292 todowrite
 285 write   185 task     98 question   63 skill  ...   15 apply_patch
```

**补丁工具在用（15 次），旧版 `patch` 工具 0 次**——旧名保留在归一化表里是零成本的防御，但不是当前的必要项。

15 条补丁调用的入参**全部**是同一形状：

```
{patchText: "*** Begin Patch\n*** Update File: <绝对路径>\n@@\n..."}
```

`patchText` 是**原文**，正文行以空格开头（这一点对解析正确性重要）。现有解析器会遍历所有字符串值寻找补丁起始标记，因此能取到正文。

**但当前实现把这个工具整个漏掉了**：发出变更前快照的钩子只认「写入」与「编辑」两个规范名，补丁类工具在钩子入口就返回空，于是既没有快照、也拿不到补丁正文。OpenCode 最主要的写文件路径目前在产物卡片上是空白的。

**同一批数据暴露的独立缺陷**：有 3 条记录（`edit` 1 条、`write` 2 条）的入参是空对象。原因是 OpenCode 会先发出**不带参数**的工具调用帧，参数随后才到。发出快照的钩子挂在第一帧上，遇到空参数即返回，**这次改动永远不会进入产物汇总**。这是与工具名无关的静默漏报，与 v2 的「参数分帧到达」修复项对应。

## 核查 3：「一轮多卡片」的真实发生率

机制上：前端的轮次切分由**真实用户消息**决定，而 sidecar 每完成一次运行时内部收尾就产出一个产物事件。某些运行时会为一条用户消息发出多次内部收尾（例如续跑轮次会合成边界）。因此同一轮可以挂出多张卡片。

从生产库统计「同一条 User Message 之下的产物事件条数」：

| 会话 | 用户消息数 | 产物事件总数 | 单条用户消息最多几张卡 |
|------|-----------|-------------|----------------------|
| …`eae92ff3` | **1** | **6** | **6** |
| …`8ee3336c` | 43 | 29 | 2 |
| …`072d6a88` | 29 | 23 | 2 |
| …`3f0bf691` | 8 | 5 | 2 |
| …`44ebb318` | 5 | 3 | 2 |
| 其余 38 个会话 | — | — | 1 |

**一条用户消息挂出 6 张卡片是实际发生过的**，多数会话在 1~2 张。因此这是「偶发但确实存在、严重时很刺眼」的问题，应从缺陷角度修复。

**附带的有利结论**：历史合成路径**已经**按用户消息切分轮次，因此把实时路径的收尾时机改成同一边界后，两条管道的轮次定义自动对齐。

## 核查 4：两套行数实现的一致性

这是本次核查最重要的发现。做法：设计 18 个边界用例，同一批输入分别喂给两套实现，逐条对照。

**4 个用例分歧，全部集中在文件末尾换行：**

| 用例 | 变更前 | 变更后 | TS 侧 | Rust 侧 |
|------|--------|--------|-------|---------|
| 无尾随换行 → 有尾随换行 | `a` | `a\n` | 0 / 0 | **1 / 1** |
| 有尾随换行 → 无尾随换行 | `a\n` | `a` | 0 / 0 | **1 / 1** |
| 去掉末尾换行 | `a\nb\n` | `a\nb` | 0 / 0 | **1 / 1** |
| 其余 14 个用例 | — | — | 一致 | 一致 |

根因：TypeScript 侧的行切分**主动丢弃末尾空行**，把「文件末尾有没有换行」当成不存在；Rust 侧把尾随换行当成真实的行变更。

**生产数据回归**：取 560 条同时带变更前后文本的真实条目，用 TS 侧算法重算，与库中存的 Rust 侧结果对比：

```
不一致：34 / 560 = 6.1%

形态高度集中于「多算 1 增 1 删」：
  stored +2/-1  vs ts +1/-0     9 例
  stored +3/-1  vs ts +2/-0     3 例
  stored +11/-1 vs ts +10/-0    1 例
  ...
反向 1 例： stored +119/-108 vs ts +120/-109
```

多数分歧即尾随换行。**反向的那 1 例是第二个根因**：两个差异算法（Myers 与 SequenceMatcher）选了不同的最小编辑脚本，因此即使修好换行语义，仍会有少量偶发分歧。

**影响评估（重要）**：前端渲染时，只要条目带变更前后文本，就**用当前 TS 算法重算行数**，并不直接读库里的数字。因此**显示给用户的一直是 TS 侧结果**，Rust 侧数字只在「既无前后文本也无补丁」的条目上被读到。这解释了为什么这个 6.1% 至今没有被用户发现——但它意味着：**一旦实现改成信任持久化行数，这 6.1% 立刻变成用户可见的错误。**

**顺带发现**：CRLF 与 LF 的整文件互转在两套实现里都计成全文件行数变更（例如 `+2 −2`）。在 Windows 上编辑器翻转一次换行符就能让卡片显示「改了 2 行」。本次不处理，记录在案。

## 核查 5：Codex 与 CLI 原生会话同步

这一项是后续追问补做的。结论：**Codex 两条来源都通；CLI 同步路径通，但对实现有两条硬约束，且原先的测试计划漏掉了这条路径。**

### Codex：两条来源都已打通

| 来源 | 工具事件怎么来 | 工具名与载荷 |
|------|---------------|-------------|
| 实时 | 文件变更项被投影成工具调用（`runtimeEvents.ts` 的 `file_change` 分支） | 名称固定为补丁类工具名；入参是**结构化的变更数组**（每项带路径与差异文本） |
| CLI 同步 | 原生 JSONL 的 `custom_tool_call` 被投影成工具调用（`codex_history.rs:311-334`） | 名称同样是补丁类工具名（`codex_history.rs:1946` 的用例确认为小写）；入参是 **`{input: "*** Begin Patch…"}`**，补丁正文嵌在嵌套字段里 |

Daemon 侧合成器对两种载荷都有解析路径：一套处理结构化变更数组，一套从入参里搜出补丁正文。因此 Codex 是四个 Agent Kind 里**唯一两条来源都已打通**的。

**但有一个数据空白必须记录**：持久化时间线中出现过的写文件工具只有 `edit` 与 `write`，补丁类工具 **0 次**。该库覆盖的时间段内没有走过 Codex 补丁路径的会话，因此 Codex 的产物覆盖**目前只有代码路径证据，没有生产数据佐证**。验收时必须主动构造一次真实 Codex 补丁改动，不能只依赖单元测试。

### CLI 同步：三条来源的实际形态差异

工具事件有三条来源，同一逻辑操作在不同来源下携带不同的名字形态与载荷形状：

| 来源 | 工具名形态 | 变更前快照 |
|------|-----------|-----------|
| 实时 | 部分被小写化（pi、Claude 钩子路径），部分原样透传 | Claude Code 与 OpenCode 有；pi 没有 |
| CLI 原生会话同步 | **保留上游原始拼写与大小写**（`codex_history.rs:294` 直接透传 `name`） | **一律没有** |
| 库内既有时间线 | 取决于写入当时 | 视当年而定 |

**硬约束一：大小写不敏感是正确性要求。** CLI 同步不做小写化，上游各 Agent Kind 的拼写各不相同。现有工具识别之所以没出问题，纯粹因为它内部做了小写归一——这条如果实现时丢掉，**整条同步来的会话会一起失效**。

**硬约束二：快照缺失是常态而非降级容错。** `file_snapshot` 在 Daemon 侧只出现在持久化与合成器里，**CLI 同步永远不产生它**（实时快照来自运行时钩子，原生日志里不存在这种东西）。这解释了实测中 736 条快照对 2271 次写操作的低比例——它是结构性的，不是随机丢失。因此退化基线必须与快照路径同等测试覆盖。

**硬约束三：同一操作的多形状都要认。** 补丁类操作在实时来源是结构化变更数组，在同步来源是一整段自由文本补丁。只实现一种就会产生「跑的时候有、刷新后没有」的分叉。

### 附带发现：工具名归一化在原地有三处，覆盖各不相同

| 位置 | 用途 | 覆盖 | 特点 |
|------|------|------|------|
| sidecar 汇总器（`turnArtifactSummary.ts:109`） | 产物汇总 | 写入 / 编辑 / 补丁 | 纯小写比较，无别名表 |
| Daemon 合成器（`turn_artifact_summary.rs:263`） | 产物汇总（历史加载） | 同上 | 纯小写比较，与上一处互为手抄 |
| 前端工具卡片（`toolHeaderSummary.ts:55`） | 工具卡片标题与参数摘要 | 读 / 写 / 编辑 / 终端 / 检索 / 任务等十余项 | 保留大小写 |

前端那处值得单独说明，因为它容易造成误判：`getToolHeaderSummary` 里有 `case 'MultiEdit'` 与 `case 'NotebookEdit'` 分支，看似支持批量编辑，但别名表里**没有** `multiedit` 条目——它能命中纯粹因为 Claude 发来的就是那个大小写。**这是巧合而非设计**，小写形态会掉到兜底分支。

**结论**：「同一个工具在一张卡上认、在另一张卡上不认」不是单个 bug，而是三张覆盖不同的表造成的结构性现象。后续若再出现此类争议，应先对照这三张表的覆盖差异，而不是各自再加一条判断。

## 意外发现

### 1. 死表 `turn_artifacts`

时间线数据库中存在一张表：

```
turn_artifacts(id, app_session_id, turn_ordinal, project_path, summary_json, created_at)
```

- 全仓库（TypeScript、Rust、文档）**零引用**，只有建表语句
- 生产库中**零行**
- 表内预留的字段形态（按轮次、按项目）说明它当年是为了「按轮次存产物」而建，但从未落地读写路径

**处置**：v2 中删除。删表不可逆，但该表从未被写入，不存在数据损失。

### 2. 操作类型字段的来源与现状

统计产物条目上的操作类型字段：

```
无值 560 条    'added' 30 条    'deleted' 30 条    'modified' 4 条
```

**带值的 64 条全部来自 OpenCode 原生汇总路径**（唯一带原生会话标识、且文件路径为相对形态的那一形状）；统一汇总器产出的 558 条**一条都没有**。这解释了为什么卡片「已渲染该字段」却从未显示过——字段从来没被填过。

### 3. 行数为零的条目全部来自图片

那 60 条「增删数均为 0」的条目**全部**来自 OpenCode 原生汇总，且都是图片文件（`static/image/...png`，操作类型为「新建」）。它们被卡片的「净变化为零则不显示」规则过滤掉，因此**一次新增 5 张图片的产物用户完全看不到**。

产品已确认维持该过滤规则；此处记录以便后续重新评估时不必重复挖掘。

### 4. 持久化事件的信封字段有多个来源

产物事件的顶层字段存在 6 种形状，可归为两类来源：实时持久化（补时间戳与序号）与历史导入（只补会话标识）。不影响前端排序与去重（走数据库列而非 JSON 字段），本次不动。

**一条被撤销的怀疑**：曾怀疑同一轮次被写了两遍产物事件。核对同一会话内每条事件的差异集合后确认——**没有任何一条重复**，形状混合只是不同轮次来自不同管道。此虚警已撤销。

## 为什么不该回填历史数据

这是本次核查最有价值的一条推导。原本的备选方案是「删掉库中所有产物事件，让历史合成路径按新算法重建，使口径统一」。**核查后否决**，理由如下。

**证据一：重建的输入与当年完全相同。**

持久化时间线中出现过的写文件工具只有两个：

```
edit  2075 次      write  196 次      （入参被截断：0）
变更前快照事件 736 条               （内容被截断：0）
```

**没有补丁类工具、没有批量编辑工具。** 因此新归一化表在这些历史事件上找不到任何新条目。

**证据二：新算法的收益 100% 在「从现在起」。**

| 新增覆盖 | 受益的 Agent Kind | 老数据里有这类事件吗 |
|----------|------------------|---------------------|
| 批量编辑 | Claude Code | 一条都没有 |
| 补丁（自由文本） | OpenCode / Codex | 一条都没有 |
| 补丁（旧名） | OpenCode | 一条都没有 |
| pi 接入 | pi | 从未产生过产物事件，无事件可删 |
| 快照匹配精确化 | 全部 | 有 736 条快照，但那是**修正量**不是**补漏**；而行数本来就会在渲染时自动重算 |

**证据三：重建可能让部分老轮次变差。**

736 条变更前快照对应 2271 次写操作，即**多数轮次没有快照**（导入会话尤其如此）。重建时这些轮次会走退化路径，前后文本精度下降。

**结论**：回填是无收益的不可逆操作，且可能降低部分老数据精度。老轮次的行数会在渲染时自动跟上新算法（前端每次渲染重算），文件清单保持现状；这个「不一致」是良性且不可避免的——它反映的是当年那次会话**确实没有产生**那些工具事件。

## 对实现的影响

| 原判断 | 核查后的修正 |
|--------|-------------|
| pi 接入需要动解析器 | **更简单**：只需挂汇总器实例，入参形状已支持 |
| OpenCode 覆盖只需要改归一化表 | **多一处改动**：快照钩子的工具白名单也要放开，否则补丁类工具拿不到正文 |
| 轮次合并可行 | 确认可行，且历史路径已是同一边界；但同时必须修「参数分帧到达」的漏报 |
| 双实现共享 fixture 是「nice to have」 | **是必需项**：分歧实测 6.1%，且有确定根因 |
| 可能需要回填历史数据 | **不需要**，且有证据表明回填有害 |
| 只有「实时」与「历史加载」两条路径 | **是三条**：漏掉的 CLI 原生会话同步路径保留上游大小写、且一律没有变更前快照；fixture 必须按「实时形状 / 同步形状」成对覆盖 |
| Codex 已覆盖，无需处理 | 覆盖成立且两条来源都通，**但无生产数据佐证**，验收须真实构造一次 Codex 补丁改动 |

## 实现后的真实数据回归

实现完成后，用生产库里**真实的轮次事件切片**跑了一遍跨语言一致性回归（不再依赖 fixture 的构造用例）：从 `session_event_snapshots` 中切出 232 个「确实含有写文件工具」的轮次（opencode 204、claude_code 21、pi 7），分别喂给两侧的**生产入口**——sidecar 的 `synthesizeTurnArtifactSummaries` 与 daemon 的 `inject_turn_artifact_summaries`——再逐条比对投影后的产物条目（file / 增删行数 / 变更前后文本）。

| 阶段 | 有分歧的轮次 |
|------|-------------|
| 修复前 | **198 / 232** |
| 修复后 | **0 / 232**（636 条产物条目逐字节一致） |

这一轮回归查出四个 fixture 没覆盖到的真实分歧，全部已修并各自补了构造用例：

1. **历史加载路径自己制造「一轮多卡片」**（影响面最大）。流末尾的「残余补发」不判断该轮是否已经收尾、是否已经有产物事件，于是一段**已经正常收尾、且库里已经存着实时那张汇总**的轮次，在每次加载历史时都会再补发一张。这就是本功能要消灭的那个问题本身，只是发生在另一条路径上。修法：残余补发加「轮尚未收尾且本轮尚无产物事件」双重条件。
2. **快照查表顺序**。daemon 侧先按工具调用查本次编辑前的快照（轮中状态），sidecar 侧先按文件查本轮首次快照（整轮基线）。前者会让同一轮里对同一文件的第二次及以后的编辑把基线挪到轮中，卡片只报最后一次编辑的局部变化——实测一个 25 次编辑的真实轮次报 `119/2`，整轮净变化实为 `120/2`。
3. **前斜杠形态的 Windows 绝对路径被当成相对路径**，在前面又拼一次 cwd，产物条目的 `file` 就成了重复路径；而卡片是按 `file` 去重的。
4. **反斜杠形态的 cwd 拼接**产生 `D:\project\x/src/app.ts` 这种混合拼写，同一个文件在实时侧与刷新后算成两个文件、卡片上出现两条。

另外验证了「同一文件在同一轮内多次编辑」的合成语义：用小到 107 个事件、单个文件的切片做最小复现，并用独立实现（Python `difflib`）算出基准答案，确认**两侧都与基准答案一致**（`3/0`、基线长度 159134 → 159377），而不是两侧互相一致却是错的。

第 3、4 条说明一件事：**路径拼写归一本身是跨语言正确性要求**，不只是风格问题。fixture 里原先所有用例的工具路径都恰好与快照路径同为前斜杠绝对路径、cwd 也都是前斜杠形态，所以这类分歧可以完全不被发现。
