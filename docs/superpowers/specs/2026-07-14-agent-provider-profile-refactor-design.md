# 智能体专属供应商档案重构设计

## 背景与目标

当前应用将 Claude Code、Codex 和 OpenCode 的供应商放在同一个 `Provider` 列表中，并在 React 层启动对话时解析、传递 API Key、Base URL、模型和 Codex 代理开关。这种模型无法表达三类智能体不同的原生配置，也使前端持有不应参与会话调用的敏感连接参数。

本次重构采用与 cc-switch 相同的“智能体专属供应商档案”模式：供应商管理页以智能体 Tab 分隔配置，激活档案时写入对应本机原生配置；新对话保持当前的智能体选择体验，仅改造供应商和模型的来源及切换副作用。

## 范围

包含：

- Claude Code、Codex、OpenCode 三个智能体的独立供应商档案、激活状态和编辑表单。
- 各智能体原生配置的读取、校验、合并、原子写入、备份与失败回滚。
- 新建对话和会话输入框中的供应商、模型加载与全局切换。
- 旧统一供应商配置的一次性迁移与兼容提示。
- 供应商切换、原生配置写入及会话启动的测试。

不包含：

- Gemini CLI 或其他未在本次需求中列出的智能体。
- 供应商官网链接字段。
- 对正在运行会话的热重配。
- 新增云端同步、凭据加密或自动故障转移能力。

## 术语与数据模型

`AgentProviderProfile` 是唯一的供应商档案模型。它包含通用元数据和按智能体区分的原生配置载荷。

- 通用元数据：`id`、`agent_kind`、`name`、`note`、`models`、`default_model`、创建与更新时间。
- 激活状态：配置根对象保存每个 `agent_kind` 对应的 `active_profile_id`，而不是保留全局唯一 `active_provider_id`。
- 会话快照：会话保存 `agent_kind`、`provider_profile_id` 和 `model`，仅用于历史展示与追溯，不保存 API Key、URL 或完整原生配置。

原生配置载荷采用受类型约束的枚举，而非把三类配置塞进统一字段：

- Claude Code：常用字段（认证、Anthropic 地址、角色模型映射、默认模型、上下文能力）及 `settings.json` 高级配置。
- Codex：常用字段（供应商标识、API 格式、Base URL、SDK 选项、模型元数据）及 `auth.json`、`config.toml` 高级配置。
- OpenCode：常用字段（供应商标识、API 格式、Base URL、SDK 选项、模型配置）及 `opencode.json` 高级配置。

同名供应商在不同智能体下互不共享。例如 Claude Code 下的“DeepSeek”和 Codex 下的“DeepSeek”是两个独立档案，各自可拥有不同的认证、模型与高级配置。

## 供应商管理界面

设置页“供应商管理”使用 Claude Code、Codex、OpenCode 三个 Tab。每个 Tab 只显示当前智能体的档案，并包含：

- 当前启用档案摘要：名称、默认模型、目标原生配置文件和启用状态。
- 档案列表：名称、接口格式、模型数量及“编辑/启用/连接测试”操作。
- 添加与编辑页面：按当前 Tab 渲染智能体专属表单，不再出现另一智能体无意义的字段。
- 高级配置区域：展示和编辑当前档案对应的原生 JSON/TOML 配置，并在保存前校验格式。

表单字段参照 cc-switch 的三种配置能力：Claude Code 支持角色模型映射，Codex 支持 `auth.json` 和 `config.toml`，OpenCode 支持扩展 SDK 选项和模型映射。供应商档案不提供官网链接字段。

## 原生配置写入

激活或修改模型都由 Rust 配置服务完成，前端不会直接读写用户目录。

1. 后端验证档案必填字段、模型、JSON/TOML 语法和目标目录权限。
2. 后端读取目标原生配置，识别 CodeMUX 管理的供应商字段；MCP、Skills、插件、权限及其他非供应商通用配置保持原样。
3. 后端合并生成新配置，先写入同目录临时文件，再以原子替换方式提交。
4. 提交前保存受影响文件的备份；任一文件写入失败时恢复本次所有目标文件，并返回文件级错误。
5. 仅在全部文件成功写入后更新 CodeMUX 中的 `active_profile_id` 和档案内容。

首次接管某智能体时，应用从本机原生配置创建“本地配置”档案，避免覆盖用户已有配置。高级配置编辑器始终在保存前展示合并后的预览或差异，避免用户无意丢失通用配置。

## 模型来源与发送框

新建对话中已有的智能体选择控件、样式和状态管理保持不变。供应商与模型控件改为以下依赖关系：

1. 当前智能体确定后，供应商控件从该智能体的档案列表读取，并标记全局启用档案。
2. 当前供应商确定后，模型控件仅加载该档案的模型配置；不再读取统一 `Provider.models`。
3. 用户切换供应商时，调用后端激活档案并写入该智能体的原生配置。成功后刷新全局配置状态和模型列表。
4. 用户切换模型时，更新当前启用档案的默认模型并写入原生配置。成功后刷新模型状态。
5. 没有可用档案或模型时禁用发送，并提供前往供应商管理页的入口。

模型获取使用按智能体区分的后端适配器：Claude Code 从角色映射和 Claude 档案配置读取；Codex 从 `config.toml` 的模型/元数据读取；OpenCode 从 `opencode.json` 的提供商模型映射读取。对支持模型列表接口的档案可提供“获取模型”，但结果必须写回当前智能体档案，不能继续使用统一 `fetch_provider_models`。

## 对话运行时边界

React 启动会话时不再解析或传递 API Key、Base URL、供应商名称、OpenCode 凭据来源、Codex 代理开关等连接配置。会话命令只提交会话 ID、工作目录、输入、智能体、权限和其他非敏感会话参数。

在启动新会话前，后端根据会话的 `agent_kind` 解析当前启用档案及其默认模型，写入会话快照。对于无法直接读取原生配置的 SDK，Rust 可以从已激活档案生成仅供 Tauri 到 sidecar 内部 IPC 使用的运行参数；这不会经过 React 状态或前端命令参数，且日志必须继续脱敏。

全局切换只影响之后新建或重新启动的会话。运行中会话继续使用启动时的运行时配置，避免 SDK、CLI 或代理在一次生成中被重配。界面应在切换成功后提示该规则。

## 旧配置迁移

启动时检测旧 `providers` 和 `active_provider_id`。迁移在保留原配置备份的前提下执行：

- 具有 Anthropic 地址的旧供应商创建 Claude Code 档案，迁移 API Key、模型、默认模型及 1M 上下文标志。
- 具有 OpenAI 地址的旧供应商分别创建 Codex 和 OpenCode 档案，迁移 API Key、模型与默认模型；Codex 代理标志转换为对应档案的兼容路由设置。
- 无法从旧字段无损推导的原生高级配置不编造值，标记为“需检查”，要求用户在对应编辑页确认。
- 只有新档案、激活状态和备份均落盘成功后才移除旧字段；失败时保留旧配置并展示可恢复的迁移错误。

## 错误处理与测试

错误消息必须区分校验失败、原生配置解析失败、文件权限/写入失败、回滚失败、连接测试失败和模型获取失败，并不得输出 API Key。

测试覆盖以下场景：

- 三类档案的序列化、反序列化、旧配置迁移和回退。
- JSON/TOML 校验、通用配置合并、原子写入与多文件失败回滚。
- Claude/Codex/OpenCode 的模型读取、模型切换和档案激活。
- 新建对话保留既有智能体选择，并按智能体加载供应商和模型。
- 前端 Tauri 调用参数不再携带敏感连接配置。
- 后端只对新会话解析新启用档案，运行中会话不重配。

## 验收标准

- 用户可在三个智能体 Tab 中独立添加、编辑、测试和启用供应商档案。
- 激活档案或更改模型后，对应原生配置正确更新，通用配置不丢失，失败能够完整回滚。
- 新建对话的智能体选择界面无视觉或交互回归；供应商和模型随智能体及档案正确联动。
- 浏览器端与前端 Tauri 调用不含 API Key、Base URL、供应商名或代理开关。
- 旧统一供应商数据可迁移，无法自动转换的部分有明确提示和可恢复备份。
