# 14 工具清单随开关(关着的能力不出现在模型面前)

**What to build:** `tools/list` 按三个开关过滤:浏览器工具随「浏览器控制」,壳侧桌面只读随「电脑控制」,驱动面(观测与输入)随「电脑控制」+「系统级执行」。关着的能力不出现在工具清单里;调用侧闸门一律不动(清单是礼貌,闸门是权威)。

**Blocked by:** 无(接在 01/04/13 的既成工具面之上)

**Status:** done

## Decisions

- **过滤,不拆服务。** spec 既定「能力只暴露为一个系统内置 MCP 服务」,分权靠 daemon 侧审批闸门;拆 server 不加护栏,只会多一份每会话子进程与工具前缀迁移成本。缺的是「关着的开关不该让模型看见工具」这条礼貌,补在过滤上。
- **分组按「调用时会拦它的那一档闸门」,不按审批风险分级。** 两者是两条轴:这里决定清单里出不出现,`guard.rs` 决定调用时要人点几下。桌面只读三件套(`computer_apps`/`computer_elements`/`computer_wait`)在审批上是只读、可记住,但执行要经驱动,所以归驱动组、跟「系统级执行」——分组跟的是**能不能跑**,不是**危不危险**。测试用调用侧事实(工具名前缀 + `desktop::op_for_tool`)独立推出期望分组,与生产的分组表交叉验证,防止两边漂移。
- **配置只读、不迁移。** 子进程直接 `serde_json` 读 `config.json`,刻意不走 `config::load_config` —— 那条路带「读不了就备份 + 重写默认值」的副作用,是权威侧的启动逻辑;一个只负责列清单的子进程不该顺手改用户配置。
- **失败开口。** 配置读不到、解析不了、目录不存在,一律按全量列出:不确定时宁可多列几个,也不让工具面静默消失(工单 05「daemon 没起就看不到工具面」、工单 07「运行时回退静默丢工具」是同类事故)。
- **每次 `tools/list` 现读,不引入 `notifications/tools/list_changed`。** 客户端重新列清单就能跟上开关变化;只列一次的老客户端仍按启动时的清单跑,调用侧由 daemon 端点闸门兜底(与既有立场一致)。列表滞后不是安全洞:关掉开关后工具还在清单里,但调用会被 403。
- **文案同步三处。** 内置 MCP 条目的描述、`computer-control` 技能「被拦住了怎么办」、设置页三个开关的说明 —— 都写明「关着的不会出现在工具清单里」以及开关改动对已在跑的会话不保证立刻生效。

## Comments

- **可见性与注入是两道闸。** 会话命令只在「浏览器控制或电脑控制开着」时才注入这份内置 server,所以「全关」组合在真实会话里不会出现;过滤矩阵里仍然断言 0 个工具,是因为它是纯函数定义域的一部分(配置被清空、会话在途),而不是可达的日常状态。
- **已知边界(如实记录):** 开关从关到开,已在跑的会话通常要新开一个会话才看得见新工具 —— 工具清单是客户端在 `initialize` 时取的,只有会重新列清单的客户端能中途跟上。调用侧不受影响(开关打开后调用即可放行);技能里已写清这条,让模型请用户新开会话而不是反复重试。
- **不动的东西:** 审批风险分级(`guard::READ_ONLY_OPS`)、允许/拒绝列表、宿主身份硬拒、步数上限、审计与轨迹,全部不因本票改变。
