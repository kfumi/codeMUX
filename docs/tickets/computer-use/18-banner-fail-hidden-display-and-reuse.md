# 18 提示条的壳侧兜底、显示器定位与窗口复用

**What to build:** 拿参考实现（ZCode 的 `windowsCuaOperationIndicator`）逐条对照我们自己的「控制中提示条」，把三处**真会骗人**或真会漏掉提示的缺口补掉：①提示条的显示与否完全由渲染层决定，渲染层失联时它会一直挂着「按 Esc 急停」；②定位固定主屏，被控窗口在副屏时提示出现在另一块屏幕上；③每段操作都重建窗口 + 重新加载页面，操作已经开始而提示还在加载。顺带把窗口层的建窗/取工作区/显示器订阅/定时做成可注入依赖，让这些不变量能在 Node 里测。

**Blocked by:** 10 控制中提示条与全局 Esc、15 常驻语义与顶部样式

**Status:** done

## Decisions

- **壳侧不再无条件相信渲染层。** 武装窗口是渲染层算出来的（「这个回合里出现过 `computer_*` 调用」），而提示条宣传的是「按 Esc 急停」—— 渲染进程卡死/被回收/WS 断链/回合状态卡在「在跑」时，屏幕上会留下一条按不动的急停提示。参考实现用的是 fail-hidden 计时器；我们的清除路径在渲染层，所以补一层**心跳**：渲染层武装期间每 5s 续期，壳侧长时间（分钟量级，见下一条）收不到就自己「解除 Esc + 收起提示条」，两件事必须一起做（只撤一半就是另一种撒谎）。
- **看门狗超时取分钟量级，不是「心跳间隔的几倍」。** 第一版按 3× 心跳取 `15s`，复核发现它会反噬：窗口被遮挡/最小化时 Chromium 把渲染层当后台页面处理（`apps/desktop/src/main.ts` 里刻意保留默认节流），5s 的定时器长时间后台后会被 intensive throttling 压到分钟级（最坏 60s 一次），于是**还活着的渲染层**被判成失联 —— 提示条与 Esc 在长时间后台操作里每 15s 拆一次，用户按 Esc 大概率没反应。现在取 `120s`（跨过节流粒度）。代价是「主线程真卡死」要两分钟才会被发现；最常见的「渲染进程直接崩掉」不走这条路径，由 main 的 `render-process-gone` 直接收尾。没有选「武装期间关掉整窗节流」：那会把遮挡期间的全部合成与轮询恢复全速，正是 `main.ts` 明确否决过的取舍，一个提示条兜底不值得翻掉它。
- **卡顿恢复要能自己站起来。** 心跳的返回值就是「壳侧现在还武装着吗」；渲染层发现自己被看门狗解除（true → false）时重新声明一次。反向的「从未武装成功」（键被别的程序占着）**不**重试注册 —— 那会变成每 5s 一次的注册风暴与日志噪音。
- **旧壳兼容。** 心跳通道缺失时（preload 未升级）退回「只在武装状态变化时同步」的老行为：提示条没有兜底，但也不该让整条武装链失败。
- **隐藏失败必须如实回报。** 窗口层 `setVisible()` 返回「目标态是否达成」：隐藏没做成 → 降级销毁并把 false 交给服务层，服务层丢掉句柄、下次显示重建。绝不允许「记账说已隐藏、屏幕上还挂着」。
- **隐藏只离场，不销毁（窗口复用）。** 隐藏改成「播完 120ms 离场动画再 `hide()`」，窗口留着复用；下一次显示立即出现（省掉建窗 + data URL 加载）。入场/离场动画因此不能再靠「重新加载页面」播：页面以 `data-state="leaving"` 起步，显示时切 `active`。
- **每次显示重申置顶。** Windows 隐藏透明窗口会清掉 `WS_EX_TOPMOST`，`showInactive()` 只恢复可见性、不恢复原生 Z-order；参考实现的做法是每次 show 都 `setAlwaysOnTop(true,'screen-saver')` + `moveTop()`，2s 轮询只留作兜底（全屏应用压过来时）。
- **定位改光标所在显示器。** 显示时用 `getCursorScreenPoint()` + `getDisplayNearestPoint()`；显示器增删/改分辨率时按**窗口当前所在矩形**重新解析（`getDisplayMatching`），而不是跟着光标跳 —— 后者会让提示条在操作中途跑到另一块屏幕上。
- **系统关掉窗口要自愈。** 「我们仍认为该显示、窗口却被系统关掉」时按 250ms 重建一次；我们自己的降级销毁（`discard` 先把 `window` 置空）不重建，否则会和失败重试互相打架。
- **窗口层自己补不回来时要上报。** 「系统把窗口关掉 + 重建也失败」时，窗口层只把自己的 `desiredVisible` 置 false 没有用：服务层的记账还是「已显示」，会把后面的显示请求全短路掉，这一整段操作里提示条再也回不来（而 Esc 还武装着）。窗口层经 `onVisibilityLost` 如实上报，服务层据此把状态改回未显示。
- **`dispose()` 是终态，退出中不接受武装。** 提示条服务 `dispose()` 之后就地失效（`setVisible(true)` 直接 no-op）；壳侧在退出中（`isQuitting`）一律把武装请求判为 false。原因是退出流程要等 daemon 停（数秒），期间渲染层的武装心跳会拿到 false 并重新声明武装 —— 那条路径会重新注册全局 Esc、重建提示条窗口，而 main 的引用已经置空，没人再收它（关机过程里闪出一条提示条）。
- **窗口复用的首帧要补状态切换。** 建窗时 `executeJavaScript(active)` 可能落在导航提交**前**的文档上，新文档一提交就把它连状态一起丢掉，于是窗口留在屏幕上、服务层与看门狗都认为显示成功，而 pill 停在 `leaving`（opacity 0）。页面加载完成后再补一次状态切换（页面加载快，肉眼仍是淡入）。
- **不照搬参考实现的两处**：它把「已排期、未开始」也算进活动（我们有意把审批等待算作武装窗口，因为提示条宣传的 Esc 在审批期间确实有效），以及它的文案/尺寸本地化机制（我们暂不做 i18n，尺寸仍按中文文案写死）。

## Comments

- **为什么不是「把判据迁到 daemon」**：那才是结构性方案（daemon 的 `computer_use/desktop.rs::execute` 是唯一知道「这台机器此刻真的在被驱动」的地方，且不依赖渲染层是否在跑），但它是新增协议面，要先落 spec + ADR。本票只修「会骗人」与「会漏提示」这两类缺陷，代价小且可回滚。
- **代价如实记录**：窗口一旦建过就长期驻留（隐藏状态，约几 MB），换来的是每段操作零延迟出现。退出路径会真销毁，不会比应用活得久。
- **没有验证的部分**：以上都是 Node 单测 + 类型门禁覆盖的行为；`showInactive`/`moveTop`/`WDA_EXCLUDEFROMCAPTURE` 这些原生效果仍需要在真机上按一遍（多显示器换屏、全屏应用压过来、Alt+Tab 后层级、截图里没有提示条）。
- **复核发现并修掉的四件事**（都是这一轮改动自己的反噬）：① 15s 超时把后台节流误判成失联（Esc 在最需要它的时候反而不生效）；② 自愈失败后服务层继续认为提示条在屏幕上；③ 退出期间心跳重声明会重建窗口并重占 Esc；④ 复用窗口的首帧可能停在 `leaving` 而整条不可见。`render-process-gone` 之所以要单列，是因为放宽超时后它才是「渲染层崩了」的即时证据（超时只负责「主线程卡死」这一类）。
- **没实测的那一半**：后台节流对 5s 定时器的具体影响取自 `main.ts` 里既有的实测结论（「定时器先对齐到 1s、长时间后台后进一步降频」）与 Chromium intensive throttling 的口径，本票没有在真机上跑「遮挡/最小化 5 分钟以上」的对照实验；取分钟量级超时在两种情形下都安全（不节流时只是晚一点发现卡死）。
