# 02 — 导航在有界渲染下仍然精确，且不再每帧读全量布局

**What to build:**

左侧回合导航在长会话里既是"位置指示器"又是"跳转入口"，它当前有两个与长会话长度绑定的问题，且必须一次解决——因为它们的失效模式是同一个：**它靠测量布局来决定行为，而布局现在可能被跳过**。

- **正确性**：依赖几何的读取（滚动时判断当前在看哪一回合、点击标记时的跳转落点、锚定修正）不再在"离屏行不参与布局"的状态下直接测量。改为在一个**显式的测量事务**内进行：进入时让相关行参与真实布局，测量与滚动完成后退出。目标是把"看起来合法的错误位置"变成"确定正确的真实位置"——长会话首次打开时早期行从未被渲染过，误差最大。
- **成本**：滚动时判断当前回合不再每帧遍历全部 User Message 逐条读取几何，改为**在布局变化时重算一次偏移、滚动期间只比较**。偏移在窗口增长、容器尺寸变化、行高变化后失效并重算。

同时把不变量钉死：**每帧执行的热循环内禁止读取布局几何**。本仓库已有"用源码契约断言约束热路径写法"的先例，沿用同一手法，使这条不变量不会在后续改动里被悄悄破坏。

跳转落点是否真的恢复精确，由 01 的真实引擎探针负责裁决——这是它存在的第一个用例。**探针已经给出结论（见下），结论改变了本工单的范围**：只做"测量逃逸口"不足以让跳转精确。

## 工单 01 的实测输入（2026-09-18，探针结论）

本工单的范围由探针结论修正过一次，原始描述（"把看起来合法的错误位置变成确定正确的真实位置"）只覆盖了一半。实测：

| 目标 | 跳过生效 | 跳过被中和 | 差值 |
|---|---|---|---|
| turn 12（较早但非第一条） | 残差 **-356.13px**（跨运行波动，另测到 -331.13 / -335.13） | 残差 **-314.94px**（五次运行完全一致） | **-41.19px**（同因不稳定，复核又测到 -16.19） |
| turn 0（字面最早一条） | 20.00px | 20.00px | 0（其上无行，被 `scrollTop` 下界截断，测不出） |

其中期望残差为 +22px（`scrollToMessage` 让目标行落在容器顶下方 22px）。拆解：

- **跳过渲染贡献 -41.19px**，由跳转途中的布局漂移差 63.89px 与滚动落点误差差 105.08px 构成。机制侧证据：with-skip 起跳前 180 行里 147 行恰为 200px 占位，其中目标行之上 20 行，目标行自身 200px→90.75px。

**根因（提交 `7a6ac8d4` 查清）**：第二条漂移不是本仓库那层 `[data-message-row]` 跳过渲染造成的，而是**streamdown 2.5.0 对每个 `[data-streamdown="code-block"]` 内联设置的 `content-visibility: auto; contain-intrinsic-size: auto 200px`** —— 第二层、嵌套的跳过渲染，工单 01 的中和规则够不到它。从未布局的代码块盒子被撑成 202px 而真实高度约 90px，**每块虚高 112.5px**；向上扫过时 3 块塌缩，把目标行上提 337.5px。量级佐证：点击时 60 个代码块里 47–54 个停在占位态，整个会话内容高度虚高 **44 × 112.5 = 4950px**，与实测 `scrollHeightDelta = -4950` 完全相等。

**已定的修法（C：跳转前稳定坐标空间 + 飞行期间保持稳定）**：用一个作用域属性同时中和两层跳过渲染（`content-visibility: visible !important`，`!important` 是必需的，要压过 streamdown 的内联样式），在**稳定后的坐标系**里计算落点，飞行期间保持该作用域，落定后移除。方案成立的关键是 `contain-intrinsic-size` 用的是 `auto`：某行一旦被真实布局过，浏览器就记住它的真实高度，因此落定后移除作用域不会让它退回占位高度。

**明确不做**：摘掉嵌套跳过渲染的永久方案（即让长会话里所有已挂载代码块都真实布局）留作**独立决策**——它能把那 4950px 的坐标虚高彻底消掉，但要付回 B 当初省下的 CPU 成本，且与工单 03 的窗口设计强相关（窗口只减少挂载行数，行高稳定性才决定 03 能否用简单锚定）。本工单不做它。
- **与跳过无关的偏差 -336.94px**（漂移 -337.50px、滚动误差 -0.56px）：被中和后**滚动动画精确落在请求位置**（误差 0.56px）⇒ `scrollToMessage` 的算式没错；偏差来自跳转途中行高变化（助手 markdown 行 304px→192px，40 行）。**这一项只修测量逃逸口消不掉。** 具体成因（可见性触发的异步升级 / 排队中的高亮补齐）已证明到"跳转前后行高改变"，未定位到确切触发点，属本工单要查的部分。

因此本工单要解决的是**两件事**：跳转落点的偏差（两条来源都要处理）与滚动期每帧的布局读取成本。只做后者、或只做测量逃逸口，都不满足验收。

另有两条与实现直接相关的实测事实：①`show:false` 的无头窗口把 rAF 压到约 1.4Hz，平滑滚动退化为瞬移，此时差值符号相反、读数不具触发条件——任何用本探针验证落点的运行都必须用逐帧动画推进的窗口模式（运行器默认已挑有效组并标注 `animationLive`）。②挂载时已渲染的行区间（0..15、底部 163..179）随视口尺寸变化，目标行必须落在"起跳时仍是占位"的区间内才测得出累计偏移。
